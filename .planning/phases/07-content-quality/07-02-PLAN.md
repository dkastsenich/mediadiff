<flagged_assumptions>
**A6 — What a video "decode error event" is.** Audio counts negative send/receive returns. MPEG-family
video decoders usually conceal a damaged slice and return success, so a count of negative returns
alone would report 0 on a visibly corrupted stream. This plan defines video's `meta.decode_errors`
value as `decode_error_count + corrupt_frame_count` (negative returns plus frames flagged
`AV_FRAME_FLAG_CORRUPT` or carrying non-zero `decode_error_flags`), with both components in
evidence. The spirit of "exactly as audio's do" (a recoverable error is counted, never fatal) is kept;
the counting unit is adapted to how video decoders report damage. Recorded in
`docs/checks/meta.decode_errors.md`.

**A7 — Phase 4's parse-only Annex-B fixtures become exit 66 in a decoding compare.**
`tools/gen_video_fixtures.py` writes H.264/HEVC streams that are "parseable, not decodable" by
construction (its own docstring). Under CONTEXT's accepted rule ("only a wholly undecodable video
stream marks the fingerprint partial and exits 66"), every decoding compare of those fixtures now
exits 66 with the report written. That is the correct product behaviour for a stream FFmpeg cannot
decode, so Task 3 re-baselines each affected exit-code assertion to 66 by name and adds an
assertion that the diagnostics carry `partial` — never by adding `--no-content`. Their fixture bytes
are never regenerated (the corpus-digest rule).
</flagged_assumptions>
