**Three value-representation decisions the engine forces, not preferences (each needs confirming):**

  - **`audio.priming` is `exact` over a `string`, not `±samples` over an `int64`.** D-14 requires
    `unknown` to compare as its own value, not as a skip. `src/compare/tol.cpp` cannot extract a
    magnitude from `Absent`, and `src/compare/engine.cpp` only short-circuits an `Absent` value when a
    `skip_reason` accompanies it — so a numeric priming value cannot also express `unknown`. The value
    is therefore the decimal sample count (`"1024"`) or the literal `"unknown"`, with
    `{state, source, samples, padding}` in evidence (D-14, D-15, D-17). Doc 05 §2's `±32 samples warn`
    wording is NOT expressible under this shape and is recorded as a deliberate divergence in
    `docs/checks/audio.priming.md`. The alternative — splitting value from state into two ids — is the
    one D-14 explicitly rejected.
  - **`audio.loudness.*` are `rational`, not `real`.** `src/compare/tol.cpp` supports only `rational`
    and `int64`; a `real` value_kind under `tol` reaches its `ErrorKind::internal` arm. Loudness and
    true peak are therefore quantised to `RationalValue{num = round(value × 1000), den = 1000}` with
    ties away from zero — deterministic, byte-identical across runs, and it satisfies PROJECT.md's
    rational-everywhere rule. libebur128's raw `double` rides in evidence at fixed precision.
  - **`audio.loudness.true_peak`'s asymmetric −1.0 dBTP rule is a GENERIC comparator escalation, not a
    second id.** `src/compare/state.cpp` does not compare two states for difference at all — it only
    asks whether either side holds a declared `flagged_value` — so a `state` id would fire whenever
    EITHER side is hot, including on an unchanged pair, which is the false-positive class this project
    treats as P0. Instead 06-08 extends `src/compare/tol.cpp`'s existing evidence-shape-gated override
    (the Rule 2 mechanism Phase 5 D-10 built for `timeline.av_offset`, never gated on `check.id`) with
    a generic "candidate crossed a declared ceiling upward" escalation driven by a
    `ceiling_state` evidence key. One id, one severity, the asymmetry intact.

**Two ids are additions beyond doc 05's literal table rows:**

  - **`audio.bit_depth`** — doc 05 §2 writes `audio.sample_fmt` / `audio.bit_depth` as ONE row with two
    extractions (`codecpar->format` and `bits_per_raw_sample`). A `CheckDef` carries one value, so it
    becomes two ids, exactly as Phase 3 and Phase 4 both already ruled for two-behaviour rows.
  - **`meta.decode_errors`** — D-09's recoverable-decode-error counter. Doc 01 §1 names
    `meta.decode_errors` as the diagnostic slot; this roster promotes it to a registered, compared
    check so a candidate that gains corrupt frames is a regression (exit 1) rather than a permanent
    "could not run". D-09 also amends doc 01 §11's "any mid-file decode error marks `partial:true` and
    exits 66" to apply only to a WHOLLY undecodable stream. **Approving this id approves that
    exit-code amendment**, which 06-10 records in the open in `docs/checks/meta.decode_errors.md` and
    as an explicit note against doc 01 §11.

**The D-05 signature composition, approved here because it is one-way** — it is written into every
snapshot envelope and is what other builds compare against. Proposed format, extending
`compose_decode_path_signature()`'s existing space-separated field list additively:

`avcodec/{M}.{m}.{u} avformat/{M}.{m}.{u} swscale/{M}.{m}.{u} triplet/{VCPKG_TARGET_TRIPLET} cpuflags/0x{hex}`

  - `triplet/` comes from a new `MEDIADIFF_VCPKG_TRIPLET` compile definition, added with exactly the
    `target_compile_definitions(libmediadiff PRIVATE MEDIADIFF_VERSION=...)` pattern `CMakeLists.txt`
    already uses, so `src/core/` still sees no libav type.
  - `cpuflags/` is `av_get_cpu_flags()`. 06-RESEARCH.md Q2 confirmed the `AV_CPU_FLAG_*` bit values are
    NOT architecture-unique (`0x1` is simultaneously `MMX`, `ALTIVEC` and `ARMV5TE`), which is exactly
    why the triplet and the flags are inseparable rather than merely additive.
  - The evidence key that carries it is the EXISTING `decode_path_class` (06-RESEARCH.md Q2's
    recommendation), whose value is `"class1"` for a class-1 stream — deliberately path-independent,
    so two class-1 fingerprints from different machines compare rather than skip — and
    `"class2 <signature>"` for a class-2 stream. No fourth key is added to `hash.cpp`'s
    `kPreconditionKeys`, so that comparator's shape is untouched.
