<objective>
Close CR-01 and CR-02 from 06-REVIEW.md (VERIFICATION.md gap 3).

CR-01 (corrected severity: latent). The sweep configures its sinks from `codecpar.sample_rate`. That value is right only because avformat_find_stream_info already decoded a frame and wrote the real rate back: "correct by accident, resting on an undocumented, load-bearing external invariant". The configuration moves to the first decoded frame.

The verifier asked for "a fixture that actually exercises a real-world implicit-SBR stream whose codecpar rate diverges from the decoded rate". `.planning/debug/audio-sweep-rate-truncation.md` proved that no ordinary container fixture reaches that divergence through the normal open path: 0 of 144 streams, and three starved-probe configurations could not force it. So this plan does not claim one. It reproduces the exact divergent state in-process instead. It opens `audio_sbr_implicit.mp4` without find_stream_info, which is the one stream the session measured going 44100 -> 88200 across that call, and drives AudioDecodeState with that header codecpar. That fails on today's code and passes after the fix, which is what the verifier's request exists to prove.

The session's one residual stays unconstructed with real media: a stream whose first packets fail inside find_stream_info but decode later. Its end state, codecpar keeping the header rate, is exactly the state the test builds, so the sweep's response to it is covered. The libav-internal path that produces it is not. That is recorded in WINDOWS.md, not claimed.

CR-02 (HIGH). After the first frame nothing re-validates a decoded frame's shape, while LoudnessSink stays pinned to the first frame. A mid-stream channel narrowing is a heap over-read on hostile input. Every frame is now checked against the recorded configuration. A mismatch stops the sweep with its reason and feeds nothing further.

Purpose: the sweep's configuration is the decoder's actual output, and no sink ever sees a shape it was not configured for.
Output: frame-derived configuration, per-frame re-validation, the tests, docs, and a corpus-wide no-change differential.
</objective>

**Contract rating.** The normalization string's `rate=` component now comes from the decoded frame. On every fixture that equals the declared rate (debug session: 0 mismatches in 144 streams), and Task 3's differential re-proves it here. The four tokens are additive. Reversibility: reversible.

**WR-09 naming concern.** CR-01's split subsumes it only partially. The declared rate gets its own explicitly named field, and `sample_rate` is documented as decoded-only. WR-09's own Fix, renaming the field to `decoded_sample_rate` and adding a WAV-reference integration test, is excluded by the orchestrator's scope, so the field keeps its name. StreamInfo's `core_rate_hz` / `effective_rate_hz` naming is an evidence contract and is untouched. 06-18 corrects WR-09's stale comment.

<assumption_delta_decision>
- **Noun now primary:** the decoded output rate. `StreamAudioDecode::sample_rate` is set from the first decoded frame and every sink is configured from it.
- **Decision:** `promote`. The declared (codecpar) rate becomes a diagnostic detail, `declared_sample_rate`, and never configures anything. Keeping the declared rate as the configuring value with the decoded one "alongside" would preserve exactly the load-bearing external invariant CR-01 names.
- **Invariant test (accepted):** 06-18 Task 2 asserts, for every AAC fixture, that `StreamInfo::effective_sample_rate_hz` equals this decoded rate. A later phase that reintroduces a declared-rate assumption turns it red.
</assumption_delta_decision>

<flagged_assumptions>
**A1: the oracle is independent of the code under test.** The CR-01 test reads the expected rate from a bare `aac_fixed` AVCodecContext decoding the same packets, not from AudioDecodeState. It also cross-checks that value against the fixture's design: tools/gen_he_aac.py uses SAMPLING_INDEX_44100 for the implicit fixture, and the debug session measured 88200 after find_stream_info. If the oracle does not report 88200, the executor stops and reports the measured value rather than editing the expectation.

**A2: layout re-validation compares the described string.** The comparison is av_channel_layout_describe output against the recorded `layout_string_`. Two exotic layouts whose descriptions truncate identically at 64 bytes would not be told apart. That affects loudness channel weighting only, never memory safety: channel count is compared separately and first.

**A3: a real stream can legitimately change configuration mid-stream,** for example a broadcast TS switching between 2.0 and 5.1 AAC. The scope's "stop, record why" rule applies: such a stream reports sampling_state "truncated" and the level checks skip with decoded_channels_changed. That is a visible degrade, not a verdict. Task 3's differential proves no corpus fixture does this. If one does, that is a Rule 4 stop, reported with the fixture and both configurations, never suppressed.

**A4: the feed_packet side-data forwarding idea from the review's CR-02 discussion is NOT taken.** The sweep sends a non-refcounted view of the caller's packet with no side data, as it does today. Changing packet side data would change what the decoder sees, and so D-01's untrimmed hash basis, which is outside gap 3.

**Perf flag:** one integer comparison per frame for channels, format and rate, plus one layout describe into a stack buffer. That is about 25,800 frames on the 600 s reference. 06-16 Task 3 measures the audio ratchet after this plan and 06-16.
</flagged_assumptions>
