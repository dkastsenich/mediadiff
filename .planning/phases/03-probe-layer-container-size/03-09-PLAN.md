<objective>
The `size.*` family: rate economics computed from the packet sweep alone, with peak windowing
defined so precisely that the result is byte-identical across platforms.

This is the direct payoff of PROBE-10's shared packet array — `size.*` derives its own statistic
from the same read-only sweep Phase 4's timeline and video work will read, with no second pass
and no pre-computed statistics struct in between.

Purpose: SIZE-01's four checks, and the first real application of D-02 — when the sweep was
truncated by D-01's budget, these checks must refuse to answer rather than answer from
incomplete data.
Output: `src/analyzers/size/size.cpp`, four registered checks with docs and fixture pairs, and a
windowing algorithm whose determinism is asserted rather than assumed.
</objective>

  <action>
    Implement windowing in `src/analyzers/size/size.cpp` as a separately-testable pure function
    over a `std::span<const PacketRecord>` plus the stream's `Rational` timebase, so the nine
    behaviors are unit-testable against hand-built arrays without generating media.

    Algorithm, exactly:
    1. Build a sorted index view over the packets by dts. Do NOT assume the read order is
       dts-sorted — `packet_scan.h` says explicitly that it is not guaranteed, and an
       out-of-order sequence fed to a naive two-pointer silently yields a too-low peak, which
       reads as clean. Sort indices, not records, to avoid copying the array the D-01 budget
       just bounded.
    2. Exclude every packet whose dts equals `AV_NOPTS_VALUE`. If none remain, emit
       `SkipReason::no_timing_data`.
    3. Compute `window_ticks` (1 second) and `step_ticks` (100 ms) in the stream's own timebase:
       `window_ticks = tb.den / tb.num` and `step_ticks = tb.den / (tb.num * 10)`, each via
       `detail::checked_div` after a `detail::checked_mul` for the denominator product. Do not
       assume `tb.num == 1` — that holds for every timebase this project's fixture list produces
       but is not a libav guarantee, and the general form costs one extra multiply.
    4. For window index k = 0, 1, 2, ..., compute `window_start = first_dts + k * step_ticks`
       FRESH from k via `detail::checked_mul` then `detail::checked_add` — never by accumulating
       `+= step_ticks`, which drifts when the step does not divide the timebase evenly.
    5. Sum the `size` of every packet whose dts falls in `[window_start, window_start + window_ticks)`,
       using a two-pointer advance over the sorted index view and `compare_ticks_checked` for the
       boundary comparisons (never `compare_ticks`, whose overflow fallback fabricates a tie and
       would silently include or exclude the wrong packets). Accumulate the byte sum with
       `detail::checked_add`.
    6. Stop when `window_start + window_ticks` passes the last dts. If the total span is under
       one `window_ticks`, emit `SkipReason::insufficient_data`.
    7. The peak is `max_window_bytes * 8` bits per second, emitted as an exact `RationalValue`
       (numerator the bit count, denominator 1, in the stream's timebase context) so the `tol`
       comparator's cross-multiplication stays exact.

    On ANY overflow at any step, emit a skip rather than a value. Never convert to double at any
    point — the cross-platform byte-identity guarantee in doc 06's own sentence depends on this
    path being pure integer arithmetic.

    `size.stream_bitrate` — per stream, `byte_total * 8 / dts_span_seconds` as an exact
    `RationalValue`, using the same dts span the windowing computed (first to last dts, excluding
    NOPTS packets). Skip with `partial_scan`, `no_timing_data` or `insufficient_data` on the same
    conditions.

    Both are PER-STREAM, at each stream's own `Scope::Kind`/index. Record in
    `docs/checks/size.peak_bitrate.md` that per-stream was the deliberate choice over a combined
    muxed-container bitrate: doc 06's row is ambiguous, `size.stream_bitrate`'s own row says

    streams with different timebases into one window — a materially harder merge the doc
    describes no algorithm for. Record in `docs/checks/size.stream_bitrate.md` that the duration
    used is the stream's own DTS span, and that doc 06 names doc 04's computed duration, which
    does not exist until Phase 4 — so a Phase-4 change here is an intentional migration, not a
    drift.

    Register both per the roster and write both docs.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| attacker-controlled packet dts values and sizes -> window boundary arithmetic | Every dts is an int64 the file chose; the window formula multiplies and divides them. |
| attacker-controlled stream timebase -> `window_ticks` / `step_ticks` division | A timebase with a zero or negative denominator would be a division by zero in the boundary computation. |
| `PacketScanResult::partial` -> the decision to answer or refuse | The truncation flag is the only thing standing between a truncated sweep and a confidently wrong bitrate. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-3-43 | Denial of Service | `window_ticks`/`step_ticks` division by a crafted timebase | high | mitigate | `detail::checked_div` (plan 03-01) rejects a zero divisor before the division executes; on x86-64 an unguarded divide by zero raises SIGFPE and terminates the process, which for a CI gate is a crash rather than a verdict. A timebase whose denominator is zero or negative emits a skip. |
| T-3-44 | Tampering | window boundary `first_dts + k * step_ticks` | high | mitigate | `detail::checked_mul` then `detail::checked_add`; an overflow emits a skip rather than a wrapped boundary that would silently window the wrong packets and report a too-low (clean-looking) peak. |
| T-3-45 | Tampering | windowed byte sum accumulation | high | mitigate | `detail::checked_add` per packet; a crafted stream of near-INT64_MAX packet sizes would otherwise wrap the sum to a small number, reporting a clean peak for a file with an enormous burst — the exact false-negative class this project treats as P0. |
| T-3-46 | Denial of Service | number of windows over a long dts span | medium | mitigate | The window count is bounded by `dts_span / step_ticks`, and the dts span itself is bounded by the packet count, which D-01's budget and the 5M-per-stream ceiling already bound. A crafted single pair of packets with a colossal dts gap would produce an enormous window count, so bound the window count explicitly and emit `skipped:insufficient_data` past the bound rather than iterating. |
| T-3-47 | Repudiation | a `partial_scan` skip a user cannot act on | medium | mitigate | The skip's evidence names the resolved per-file byte cap and the packet counts reached, so a user knows to raise `--probe-memory-budget-mb` or lower `--threads`. A skip with no remediation path is only half a mitigation. |
| T-3-SC | Tampering | package installs | low | accept | No package installed; FFmpeg 8.1 pin unchanged (03-RESEARCH.md Package Legitimacy Audit: not applicable this phase). |
