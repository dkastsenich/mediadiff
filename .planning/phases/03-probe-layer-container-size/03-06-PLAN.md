    Implement the vint reader as two explicit functions, `read_element_id` (marker bit RETAINED —
    Matroska element IDs are conventionally written with their full encoding, which is why the
    doc's IDs read as `0x1F43B675` rather than a stripped value) and `read_element_size` (marker
    bit STRIPPED, and the all-ones VINT_DATA case reported as unknown-size, never decoded as a
    length). Reject a `0x00` leading byte outright. Both return failure rather than a value on
    any malformed input, and every failure ends the walk with the current offset.

    Public shape: `struct EbmlTrack { std::uint64_t track_number; std::optional<std::int64_t> codec_delay_ns; std::optional<std::int64_t> seek_pre_roll_ns; std::string codec_id; std::optional<std::int64_t> sampling_frequency_hz; }`,
    and `struct EbmlScanResult { std::optional<std::int64_t> seek_head_offset, info_offset, tracks_offset, first_cluster_offset, cues_offset; std::optional<std::uint64_t> timestamp_scale; bool has_duration_element; std::vector<EbmlTrack> tracks; bool complete; std::int64_t stop_offset; }`.
    Use `std::optional` for `codec_delay_ns` and `seek_pre_roll_ns` specifically so "the element
    was absent" is distinguishable from "the element said zero" — Matroska's own default for a
    missing `CodecDelay` is zero, and collapsing the two would make an added explicit zero
    invisible.

    Record the track's `SamplingFrequency` (element `0xB5`, a float in EBML) as an integer hertz
    value where it parses cleanly, because plan 03-06 Task 2 needs it to convert `CodecDelay`
    nanoseconds into the `samples` unit the roster declares. Where it does not parse cleanly,
    leave it absent — the check then skips rather than dividing by a guess.

    Follow `SeekHead` only under all three guards: the target offset is within the file, reading
    four bytes there succeeds, and those bytes decode to the expected element ID. A failure of
    any guard records `Cues` as not located; it never ends the whole walk (a broken `SeekHead` in
    an otherwise-valid file is a seeking-metadata defect, not a corrupt container) but it does
    record the condition in the result so the analyzer can put it in evidence.

    Bound `SeekHead` following to a single hop with no recursion — a `SeekHead` that points at
    another `SeekHead` that points back is otherwise an infinite loop, and one hop is all doc 02
    asks for.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| raw Matroska bytes -> `ebml_scan`'s vint reader | Every element ID and size is a variable-length integer the file chooses; a vint can encode a value up to 2^56-1 in a size field. |
| `SeekHead` target offset -> absolute file seek | This is the only place in the phase where a scanner seeks to an offset the FILE chose, rather than one it computed by walking forward. That makes it the sharpest primitive in the phase. |
| `container.format` measurement value -> engine demotion decision | The format string reaches the engine from a fingerprint that may have been read from an attacker-influenced `*.snap.json`. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-3-25 | Tampering | EBML size vint driving a walk advance | high | mitigate | Every decoded size is range-checked against the bytes remaining before it advances the cursor, through `detail::checked_add`; the reserved all-ones VINT_DATA form is recognized as unknown-size and never decoded as a huge length; a `0x00` leading byte is rejected outright. Behaviors 2, 3 and 4. |
| T-3-26 | Tampering | `SeekHead` absolute-offset following | high | mitigate | Three guards, all required: the target is within the known file length, reading four bytes there succeeds, and those bytes decode to the expected element ID. Following an unverified content-derived offset is an arbitrary-read primitive; doc 02's own "seek to offset, verify ID" wording is the requirement, and behavior 7 asserts both rejection cases. |
| T-3-27 | Denial of Service | `SeekHead` chain | high | mitigate | Following is bounded to a single hop with no recursion — a `SeekHead` pointing at another `SeekHead` pointing back would otherwise loop forever inside a CI job. |
| T-3-28 | Denial of Service | zero-size or non-advancing element | high | mitigate | The strictly-increasing-offset guard `bmff_scan` established is reused verbatim; a size that advances by zero or backwards ends the walk. |
| T-3-29 | Tampering | `CodecDelay` nanoseconds x sampling rate | medium | mitigate | `detail::checked_mul` then `detail::checked_div`; an overflow or an unknown rate emits `skipped:insufficient_data` rather than a wrapped sample count. A wrapped value here would be a plausible-looking number that fails a `1samples` tolerance for the wrong reason. |
| T-3-30 | Spoofing | a crafted `container.format` value in a snapshot steering the demotion | medium | mitigate | The demotion only ever converts findings TO `skipped`; a spoofed family token can suppress mechanism checks but cannot manufacture a `pass`, and `skipped != pass` is enforced engine-wide. `container.format` itself is never demoted, so the format claim is always visible in the report. |
| T-3-SC | Tampering | package installs | low | accept | No package installed; FFmpeg 8.1 pin unchanged (03-RESEARCH.md Package Legitimacy Audit: not applicable this phase). |
