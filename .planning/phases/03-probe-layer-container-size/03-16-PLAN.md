<flagged_assumptions>

across platforms.** `scripts/gen_corpus.sh`'s own header and 03-14-PLAN.md's
`<flagged_assumptions>` both state the governing fact: `-flags +bitexact -fflags +bitexact`
guarantees determinism for a **given encoder build**, not across builds. A pinned Linux
x86_64 binary, a pinned Linux aarch64 binary, a pinned macOS arm64 binary and a pinned Windows
x86_64 binary are four different binaries — possibly different configure flags, different SIMD
paths. Task 3 therefore ships per-leg digest evidence rather than an assertion, and plan 03-19
evaluates that evidence before the golden policy is declared closed. **Expect the macOS and
Windows legs to be red on the fixture-derived goldens after this plan lands if identity does
not hold** — that is a measurement, not a regression, and 03-19 owns the response.

    **Step B — write `scripts/install_pinned_ffmpeg.sh`.**
    A new tracked, executable script following the shape of `scripts/check_corpus.sh`. It:
    - derives the runner key from `uname -s` and `uname -m`: `Linux`+`x86_64` to
      `linux-x86_64`; `Linux`+`aarch64` or `arm64` to `linux-aarch64`; `Darwin`+`arm64` to
      `macos-arm64`; a `MINGW`/`MSYS`/`CYGWIN` prefixed `uname -s` with `x86_64` to
      `windows-x86_64`. An unrecognised pair exits non-zero naming the exact observed
      `uname -s` and `uname -m` values.
    - reads `scripts/ffmpeg_pin.json` with `python3` (already installed by the workflow's
      `Set up Python (3.11 series, for the Phase 2 registry generator)` step and present on
      every runner) rather than hand-parsing JSON in shell.
    - downloads the entry's `url` to a temporary directory over HTTPS with `curl -fsSL`, then
      computes SHA-256 with the first available of `sha256sum`, `shasum -a 256`,
      `openssl dgst -sha256`. If NONE of those exists, exit non-zero — never proceed
      unverified.
    - compares the computed digest to the entry's `sha256` and, on any difference, prints both
      digests, the URL, and a refusal line, then exits non-zero. There is no retry-with-a-
      different-source path and no path that continues to use a binary whose digest did not
      match, because a supply-chain substitution that degrades into "use whatever is on the
      machine" is worse than a red build.
    - extracts by the entry's `archive` kind into the temp directory, resolves `ffmpeg_path`,
      and asserts the resolved path is a regular executable file inside the extraction
      directory. Refuse and exit non-zero if it is not, so an archive with a traversal entry
      cannot place a binary elsewhere and have it be used.
    - runs the pinned binary's `-version`, `-encoders` and `-muxers` and asserts the codec and
      muxer names listed in Step A are all present, exiting non-zero naming the first missing
      one.
    - prints the resolved absolute path and the version line, then — when `GITHUB_ENV` and
      `GITHUB_PATH` are set — appends `MEDIADIFF_FFMPEG=<absolute path>` to `GITHUB_ENV` and
      the binary's containing directory to `GITHUB_PATH`. Appending to `GITHUB_PATH` is
      load-bearing, not cosmetic: the Windows-only PowerShell cross-check step clears
      `MEDIADIFF_FFMPEG` and then requires an ffmpeg on PATH.
    - when run outside Actions (no `GITHUB_ENV`), prints an `export MEDIADIFF_FFMPEG=<path>`
      line to stdout so a developer can evaluate it, and still exits 0. This is the local
      regeneration path Task 2 uses.
    - includes the project's zero-file guard: if `scripts/ffmpeg_pin.json` is missing or its
      `builds` object is empty, exit non-zero with the established two-line refusal message
      shape.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| third-party download host to CI runner | An archive fetched over the network becomes an executable that synthesizes every test fixture; its output defines what "clean" means for the release blocker. |
| archive contents to runner filesystem | Extraction writes attacker-influenced paths onto the runner. |
| fork-originated PR to workflow environment | A fork run executes this workflow with attacker-authored repository content. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-3-78 | Tampering | `scripts/install_pinned_ffmpeg.sh` download of a third-party ffmpeg archive | high | mitigate | SHA-256 pinned in `scripts/ffmpeg_pin.json` and verified before extraction; mismatch prints both digests and exits non-zero; no fallback path to an unverified or system binary; HTTPS-only URL; a dated release tag rather than a rolling one where the provider offers both. |
| T-3-79 | Tampering | archive extraction in `scripts/install_pinned_ffmpeg.sh` | medium | mitigate | Extract into a dedicated temporary directory; resolve `ffmpeg_path` and assert it is a regular executable file located inside that directory before invoking it; refuse otherwise. |
| T-3-80 | Denial of Service | pinned provider availability | medium | accept | A provider outage or asset deletion fails the install step loudly on every leg. Accepted because the alternative — a silent fallback to a rolling channel — reintroduces the exact defect this plan closes. Re-pinning is a one-file edit, and the provider and version are recorded in `scripts/ffmpeg_pin.json` so the re-pin is mechanical. |
| T-3-81 | Elevation of Privilege | `MEDIADIFF_FFMPEG` inherited from the environment | low | accept | The workflow sets `MEDIADIFF_FFMPEG` itself, after the verified install, overwriting anything inherited; no workflow input flows into the pin manifest or the URL. |
| T-3-82 | Repudiation | fixture provenance | medium | mitigate | `tests/fixtures/GENERATOR_MANIFEST.json` records the pinned build that produced the corpus, and `scripts/corpus_digest.sh` emits a per-fixture digest listing per leg, so "which binary produced these bytes" is answerable from the run log. |
| T-3-83 | Spoofing | golden re-baselining path | high | mitigate | The three TSDuck goldens are an independent reference; refreshing them through the renderer path would silently substitute this project's own output for ground truth. Task 2 requires `scripts/capture_tsduck_golden.sh` and records the command actually run; `scripts/lint_tsduck_goldens.sh` keeps the presence gate. |
