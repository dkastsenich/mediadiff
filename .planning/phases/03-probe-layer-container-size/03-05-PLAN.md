    Create `src/probe/bmff_scan.{h,cpp}`, independent of libav (no libav header included).

    Public shape: `struct BoxRecord { std::array<char,4> type; std::int64_t offset; std::int64_t size; }`,
    `struct EditListEntry { std::int64_t segment_duration; std::int64_t media_time; std::int32_t media_rate_integer; std::int32_t media_rate_fraction; }`,
    `struct BmffTrack { std::uint32_t track_id; std::uint32_t media_timescale; std::vector<EditListEntry> edits; }`,
    `struct BmffScanResult { std::vector<BoxRecord> top_level; std::string major_brand; std::uint32_t minor_version; std::vector<std::string> compatible_brands; std::uint32_t movie_timescale; std::vector<BmffTrack> tracks; std::int64_t moof_count; bool has_sidx; bool complete; std::int64_t stop_offset; }`.
    `complete == false` with `stop_offset` set is the ONLY way the scanner reports a structural
    problem — it never returns a partial result that looks whole.

    Entry point: `mediadiff::expected<BmffScanResult, Error> run_bmff_scan(const std::string& utf8_path)`.
    Read the file through a bounded reader that owns the file handle and exposes only
    "read N bytes at the current position" and "seek to absolute offset O", where BOTH operations
    validate against the known file length first and return failure rather than reading. Every
    size arithmetic step — `offset + size`, `entry_count * entry_size` — goes through
    `detail::checked_add`/`checked_mul` from `src/core/rational.h`; a failed check ends the walk
    with `complete = false` and the current offset, exactly as an out-of-range size does. Record
    inline that this is the same discipline `rational.h` exists to enforce for time arithmetic,
    applied to byte offsets because the inputs are equally untrusted.

    Enforce a minimum advance: after each top-level box, the next offset must be strictly greater
    than the current one. A size that would advance by zero or backwards ends the walk. This is
    the guard against a crafted infinite loop and it must be an explicit check, not an emergent
    property of the arithmetic.

    Read integers big-endian explicitly, byte by byte into a `std::uint32_t`/`std::uint64_t` —
    never a `memcpy` into a struct and never `ntohl`. This is portable across every target
    toolchain and endianness by construction, which matters because determinism must hold across
    platforms, not merely across runs.

    Descend into `moov` only as far as doc 02 lists: `mvhd` for the movie timescale, and each
    `trak`'s `tkhd` (track_id), `mdia`/`mdhd` (media timescale) and `edts`/`elst` (edit entries).
    Handle version 0 and version 1 field widths for `mvhd`, `tkhd`, `mdhd` and `elst`; the version
    byte is the first byte of each full-box's 4-byte version-and-flags word. Never descend into
    `stbl` or any sample table — that is payload-adjacent and outside PROBE-04's stated scope.

    Wire `Pass::bmff_scan` into `src/probe/orchestrator.cpp`'s union executor and add a
    `std::optional<BmffScanResult> bmff` member to `ProbeResults`. The pass is requested only
    when `ContainerFamily::mp4` — running it on an MKV or TS input is forbidden by the
    family-scoping rule plan 03-02 established.

    Add `tests/unit/test_bmff_scan.cpp`. Behaviors 3, 4, 5 and 9 need adversarial inputs;
    construct those as byte buffers in the test itself (hand-written box headers) rather than
    generating media, so the malformed cases are exact and committed as C++ source, not as
    binaries. Behavior 9's truncation cases operate on a real fixture read into memory and
    truncated in the test.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| raw MP4 bytes -> `bmff_scan`'s own parser | The first parser in this project whose arithmetic operates directly on attacker-controlled length fields. Every box header is a 32- or 64-bit size the file chooses. |
| `ftyp` brand strings and `elst` entries -> `Measurement` value and evidence -> report | File-content-derived strings and integers flow into compared values and rendered output. |
| `bmff_scan`'s absolute seeks -> file handle | `SeekHead`-style offset following is not used here, but `moov` descent computes absolute offsets from content-derived sizes. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-3-19 | Tampering | box `size` / `largesize` field arithmetic | high | mitigate | Every `offset + size` and `entry_count * entry_size` goes through `detail::checked_add`/`checked_mul`; a failed check ends the walk with an exact `stop_offset` instead of wrapping to a small (or negative) value that would pass a naive range test. Behaviors 3 and 4, asserted on exact offsets. |
| T-3-20 | Denial of Service | a box whose size does not advance the cursor | high | mitigate | An explicit strictly-increasing-offset guard after every top-level box; a size of 0..7 (or 0..15 in largesize form) ends the walk. Without this a crafted 8-byte-header box declaring size 0 in the non-final position loops forever inside a CI job. |
| T-3-21 | Tampering | `elst` `entry_count` driving a read loop | high | mitigate | `entry_count` is validated against the `elst` box's own remaining bytes BEFORE any entry is read, so a declared count of 2^32-1 allocates and reads nothing. |
| T-3-22 | Tampering | absolute seek during `moov` descent | high | mitigate | The bounded reader validates every seek target against the known file length and returns failure rather than seeking; the scanner has no code path that seeks to an unvalidated content-derived offset. |
| T-3-23 | Information Disclosure | brand strings and `elst` values -> terminal | high | mitigate | Brand strings are 4-byte fixed-width and constrained by construction; free-form text from this scanner is limited. The general control-byte exposure (T-2-33) is closed once at the render boundary in plan 03-11, before any verbose rendering of scanner evidence ships. |
| T-3-24 | Denial of Service | a file with an enormous number of top-level boxes or tracks | medium | mitigate | `top_level` and `tracks` grow only as far as the file's own bytes allow — each record consumes bytes of input, so the vector size is bounded by file size divided by the 8-byte minimum header, not by a declared count. |
| T-3-SC | Tampering | package installs | low | accept | No package installed; FFmpeg 8.1 pin unchanged (03-RESEARCH.md Package Legitimacy Audit: not applicable this phase). |
