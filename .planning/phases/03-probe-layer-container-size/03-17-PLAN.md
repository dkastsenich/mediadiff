<objective>
Two source-level defects that block or degrade this phase's shipped work, both scoped by
locked decision **D-GAP-02** items (a) and (d).

(a) The `x64-windows-static-md` blocking leg fails at the `Build` step with
`error C2059: syntax error: ')'` on `std::max(1.0, std::abs(value))` at
`src/probe/ebml_scan.cpp:348`. `src/util/fs.h` includes `<windows.h>` on `_WIN32`, which
defines function-like `min`/`max` macros; the symbol is defined nowhere in this project's own
sources or CMake files (confirmed by `03-VERIFICATION.md`'s own `grep -rn` spot-check, which
found matches only inside third-party vcpkg ports). The same line carries a second, latent
defect: `src/probe/ebml_scan.cpp` calls `std::max` without including `<algorithm>` — its
sibling `src/probe/bmff_scan.cpp` does include it. TRUST-06 and every other Phase-3 check has
therefore never been proven to build on the toolchain PROJECT.md names as a hard parity
requirement.

(d) `src/report/junit.cpp`'s `xml_escape` escapes illegal C0/DEL bytes as visible `\xHH` text
but omits the backslash-doubling that `src/util/sanitize.cpp`'s `sanitize_for_display` applies
to the same byte class, so a real ESC byte and text that literally spells its escape form
render identically in a JUnit report (03-REVIEW.md WR-01, non-gating).

Purpose: the Windows leg cannot contribute to SC5 until it compiles, and the file's own head
comment claims a parity with `sanitize_for_display` that the code does not yet deliver.
Output: a compile-clean MSVC path and an unambiguous JUnit escaper, both covered.
</objective>
