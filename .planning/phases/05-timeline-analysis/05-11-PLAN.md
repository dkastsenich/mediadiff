<flagged_assumptions>
**A1 — the drop-frame string form is `05-RESEARCH.md`'s open question 1 and is resolved empirically in
Task 1, not assumed.** The research verified a NON-drop-frame `tmcd` fixture renders `00:00:10:00` with
all colons, and records as an assumption (A1 in its own log) that a drop-frame rate would render
`HH:MM:SS;FF` with a semicolon. Its own recommendation is that "the planner's first timeline plan should
generate a drop-frame `tmcd` fixture and inspect the raw metadata string ... before committing to a parse
implementation". Task 1 does exactly that. If the semicolon does NOT appear on this no-decode path, the
fallback recorded there is to derive the drop-frame state from the timecode RATE (29.97 / 59.94) rather
than from string punctuation, and that fallback is implemented instead — with the observed string
recorded in the SUMMARY either way.

**A2 — TIME-11's two edges are authored in `must_haves` above.** `empty` (no `tmcd` track) is resolved as
an explicit comparable absence rather than an empty string; `encoding` (whose definition of equality
applies) is resolved as a byte-exact comparison of the string libav publishes, after the project's
existing display-sanitisation choke point and with no normalisation of any kind.

**A3 — `timeline.timecode.value` uses the `exact` semantic on a string that may be `Absent{}`.** Under
`src/compare/exact.cpp` an `Absent{}` on one side and a string on the other is a difference, which is the
desired behaviour: a timecode that disappears between two builds must be reported. Confirm that
comparator arm before relying on it; if `exact` treats an absent-versus-present pair as a skip rather than
a difference, the `presence` id already covers appearance and disappearance and this fact should be
recorded in the SUMMARY rather than worked around.
</flagged_assumptions>
