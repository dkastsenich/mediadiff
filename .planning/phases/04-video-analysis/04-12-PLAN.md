<flagged_assumptions>
**A1 — The DOVI fixtures are hand-written boxes, not encoder output.** Research Priority Finding 2
established that genuine Dolby Vision RPU encoding is unreachable in this toolchain on any binary,
GPL or not, because it requires externally-supplied per-frame RPU metadata no tool in this stack
can produce. Plan 04-05 wrote the configuration record by hand instead. That is sufficient for
`video.hdr.dovi` and `video.hdr.dovi.config`, which compare the configuration record only — and it
is exactly why per-frame RPU diffing is out of scope for v1 rather than merely deferred.

**A2 — Coherence is a state, not a regression.** VIDEO-10 asks for a note "even when both files
share it". Under an `exact` comparison two files sharing a state compare `pass`, and the state is
visible as the check's VALUE in `inspect` and in the finding's rendered values in `compare -v`.
That is the design doc's own framing: visible in `inspect`, non-gating in `compare`. A reader
expecting a `compare` finding whenever incoherence exists on both sides will not get one, and
should not — the check reports what the file is, and a difference between two files is what
`compare` is for. State this plainly in the check's own doc so the behaviour is documented rather
than surprising.

**A3 — Spec-less edge probe.** The last of the 17 unresolved probe items is authored into this
plan's `truths`: **VIDEO-10-E1** — a file compared against a byte-identical copy, where both carry
the same incoherence, still surfaces that incoherence and still does not gate the exit code.
With this, all 17 probe-surfaced items are accounted for across the phase's twelve plans.
</flagged_assumptions>

`04-CONTEXT.md` D-10 is the phase's only decision rated **one-way**: check IDs are forever, and
renaming one post-v1 requires an alias plus a deprecation cycle. Plan 04-01's roster gate approved

vocabulary is compared, rendered, and written into every snapshot — it is as permanent as the id.

Proposed spelling: `video.hdr.coherence`, group `video`, semantic `exact`, unit `none`,
value_kind `string`, severity `info`, no tolerance, no profile overrides.

Proposed value vocabulary, a closed set:

  `coherent`             the transfer characteristic and the HDR metadata agree — either a PQ or
                         HLG transfer with mastering-display metadata present, or an SDR transfer
                         with none.
  `hdr_meta_sdr_transfer` mastering-display or content-light metadata is present while the transfer
                         characteristic is an SDR one.
  `pq_without_mdcv`      the transfer characteristic is PQ or HLG but no mastering-display metadata
                         is present.
  `indeterminate`        the transfer characteristic is unspecified, so no coherence claim can be
                         made in either direction.

Three properties follow from this shape and are worth confirming explicitly rather than
discovering later:

  - Under an `exact` comparison, two files that SHARE an incoherence compare `pass`. The state is
    still visible — as the check's own value in `inspect`, and in the finding's rendered baseline
    and candidate values in `compare -v`. That is doc 03 §4's own framing ("visible in `inspect`,
    non-gating in compare") and VIDEO-10's "even when both files share it". If you expect a
    `compare` finding to appear whenever incoherence exists on either side, say so now — that is a
    different check and a different severity model.
  - `indeterminate` exists so that a file with an unspecified transfer does not get labelled
    coherent by default. Most of this corpus's `mpeg4` fixtures will report it.
  - `info` severity means this check never gates the exit code, in any profile. That is D-10's own
    specification and is not a tuning decision.

The alternatives D-10 already rejected, restated so this checkpoint is a real choice: hanging the
note on `video.hdr.mdcv`'s evidence (invisible when that check itself reports `pass`, and in the
`pq_without_mdcv` case attached to a check whose own value is "not present"), or on
`video.color.transfer`'s evidence (same invisibility problem, and it puts an HDR-metadata fact on a
colorimetry check).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| attacker-controlled `dvcC` payload -> the configuration-record read | The box's payload size and contents are chosen by the file, and the linked parser accepts payloads well under the nominal 24 bytes. |
| two independent extractions -> one classification | The coherence value is a function of two file-controlled facts; a mis-read of either produces a confident, wrong state. |
