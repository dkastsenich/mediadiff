## Where this plan departs from `G-02-7`'s framing, and why

`G-02-7`'s second bullet says: "determine which `ErrorKind` a nonexistent path produces on Windows and why it maps to 64 rather than 65 … Fix the mapping, not the test's expectation." The mapping is already right, and reading it is what shows the divergence is upstream:

- `src/cli/exit_code.cpp` maps `ErrorKind::input_open` to `kExitInput` (65) and `ErrorKind::usage` to `kExitUsage` (64), unconditionally, with no `default:` arm and no platform conditional. Nothing in it can differ between platforms.
- `src/core/snapshot.cpp:25-27` produces `Error{ErrorKind::input_open, "could not open snapshot file: " + utf8_path}` when `fopen_utf8` fails, which is what a nonexistent path does on every platform.
- So a nonexistent path exits 65 — **provided the argument reaches `read_snapshot` at all.**

On Windows it does not. `tests/integration/test_exit_codes.cpp:94` passes `/no/such/file.snap.json`, and CLI11 2.6.2 declares `bool allow_windows_style_options_{#ifdef _WIN32 true #else false #endif}`. `src/cli/main.cpp` never calls `allow_windows_style_options(...)`, so on Windows a leading `/` makes CLI11 classify the token as an option. mediadiff defines no `/`-prefixed option, so the parse throws, `src/cli/main.cpp:86` returns `app.exit(e)` mapped to `kExitUsage`, and the CHECK expands to `64 == 65`. The path is never opened, the `ErrorKind` is never produced, and the mapping never runs.

The fix is therefore still in the product and still not in the test's expectation — it is simply one layer up, in argv classification. `/data/out.snap.json` is a legitimate path on Windows (the Win32 APIs accept forward slashes and resolve it against the current drive), so the default is not merely inconvenient for a test: it silently reclassifies real user input on one platform. Turning it off restores exact cross-platform argv parity, which is the same posture `src/cli/main.cpp:49` already takes for prefix matching and the same posture PROJECT.md takes on determinism generally.

**The rejected alternative, named so it is not rediscovered.** Changing the test's argument to a non-option-shaped nonexistent path would also make the test green, and would be defensible on the narrow reading that "a nonexistent input path" is what the test is about. It is rejected: it greens the assertion while leaving the product mis-classifying forward-slash-rooted paths on Windows, which is the failure the test accidentally found. `must_haves.prohibitions` forbids it.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user argv → mediadiff's parser | Where a token becomes either an option or a path. Classifying a path as an option means the named file is never opened while the process still reports a definite answer — for a CI gate, the wrong definite answer. |
| mediadiff exit code → the caller's CI script | `CLI-06`'s contract is the entire machine-readable surface of this tool: `<3` is a finding, `>=64` is "no verdict was produced". A 64 where 65 belongs tells a CI script the user's flags were wrong when in fact their input was missing. |
| local worktree → origin / PR #2 | The push is the delivery step; after it the code is observable by CI and anyone watching the PR. |
| GitHub Actions job log → this round's verdict | The run log is the sole evidence for every Windows claim this round makes. Reading it selectively is how a phase certifies itself on a partial truth — this phase has already done that once. |

Nothing in this plan adds a runtime input, a network call, a filesystem boundary or a dependency. The parser change *narrows* what mediadiff accepts on one platform.
