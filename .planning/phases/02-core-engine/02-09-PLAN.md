<objective>
Render the fourth report format — the one a human actually reads — with findings
grouped in a fixed order, only non-pass shown by default, the accept/tune/silence
triple under every gating finding, and a colour decision that gets CI right.

Purpose: the accept/tune/silence triple is one of the project's three
non-negotiable properties. A gating finding a user cannot act on is a finding
they will eventually silence wholesale, and a wholesale silence is a muted gate.
Output: `src/cli/tty_render.{h,cpp}` and the one place the colour question is
answered.
</objective>

Implement `src/cli/color_policy.{h,cpp}` as the single place the colour question
is answered, so no renderer re-derives it.

`struct ColorInputs { bool stdout_is_tty; std::optional<std::string> no_color; std::optional<std::string> ci; std::optional<std::string> github_actions; bool flag_no_color; bool flag_ascii; };`
and `struct ColorDecision { bool color_enabled; bool ascii_glyphs; };` plus a
pure `ColorDecision decide_color(const ColorInputs&)` that takes every signal as
data rather than reading the environment itself — which is what makes the whole
matrix unit-testable without spawning a process or mutating the test runner's
environment.

The decision, in this precedence order: `--no-color` disables colour
unconditionally; otherwise `GITHUB_ACTIONS` equal to the literal `true` keeps
colour enabled even though `CI` is also set there, because GitHub's log viewer
renders ANSI; otherwise `NO_COLOR` present with any value at all disables colour,
per that convention's own rule that presence is the signal, not the value;
otherwise `CI` equal to the literal `true` disables colour; otherwise colour
follows whether stdout is a TTY. `--ascii` is independent: it swaps the check,
warning, cross and info glyphs for the words `OK`, `WARN`, `FAIL` and `INFO`
whether or not colour is on, because a terminal that cannot render the glyphs is
a different problem from one that cannot render colour.

A thin `ColorInputs read_color_inputs(const CliOptions&)` in `options.cpp` is the
only place `getenv` and the TTY test are called. Windows VT enablement is already
handled by `enable_vt_output` in the entry point and must not be duplicated here.

`tests/unit/test_color_policy.cpp`, tag `[color]`, table-driven over the full
matrix: TTY with nothing set gives colour; non-TTY gives none; `NO_COLOR` empty
string still disables; `NO_COLOR` with a value disables; `CI=true` disables;
`CI=true` plus `GITHUB_ACTIONS=true` keeps colour; `CI=false` does not disable;
`--no-color` beats `GITHUB_ACTIONS=true`; `--ascii` sets `ascii_glyphs` in every
colour state. Each row asserts both fields of the decision, so a change that
accidentally couples the two is caught.

Implement `src/cli/tty_render.{h,cpp}`:
`std::string render_tty(const ReportModel&, const CheckRegistry&, const ColorDecision&, int terminal_width)`.
It returns a fully composed string and writes to no stream, matching the
`compose_version_string` pattern; `compare.cpp` is what prints it. Taking
`terminal_width` as a parameter rather than querying the terminal keeps the
renderer unit-testable at any width.

Layout: a one-line summary, then each group in the `ReportModel`'s group order
with its findings. Only non-pass findings are shown unless `RenderOptions::show_pass`
is set by `-v`; ignored-but-differing findings — the `volatile` ones — appear only
under `-v`, carrying their real values, because a value the tool declined to gate
on is still a value the user is entitled to see. Columns are laid out to the given
width; a value too wide for its column is elided with a trailing marker rather
than wrapped, since a wrapped value column makes a diff unreadable at exactly the
moment the user needs it.

Status glyphs come from the `ColorDecision`: the symbol set when `ascii_glyphs`
is false and the words `OK`, `WARN`, `FAIL`, `INFO` when it is true. Styling goes
through `fmt::emphasis` and `fmt::fg` from `<fmt/color.h>`, included separately
from `<fmt/format.h>`, and every styled call is gated on
`ColorDecision::color_enabled` so a disabled decision emits no escape byte at all
rather than emitting an empty style.

The accept/tune/silence triple (REPORT-03) prints under **every** gating finding
individually — never once per group — in the fixed order accept, tune, silence.
Its content is the third documentation section compiled into the binary by the
generator. To make that section machine-usable rather than free prose, extend
`tools/gen_registry.py` to split `## Accept / Tune / Silence` into three labelled
sub-parts keyed by the level-3 headings `### Accept`, `### Tune` and `### Silence`,
require all three to be present, and carry them into `CheckDef` as separate
string views. A check with no meaningful tune knob writes `### Tune` with the
explicit text stating none applies, so the renderer prints the label with that
text rather than silently omitting a third of the triple. Update the three
shipped `docs/checks/*.md` files and the test-registry docs under
`tests/support/docs/` to the new three-sub-heading structure; the generator's
existing structure check makes a doc that was not updated a build failure, so
none can be missed. A non-gating finding prints no triple.

`tests/unit/test_tty_render.cpp`, tag `[tty]`: groups render in the fixed order;
only non-pass findings appear without `-v` and pass findings appear with it; a
gating finding prints its triple and a non-gating one prints none; two adjacent
gating findings each print their own triple, asserted by counting occurrences of
the accept label; the triple's three labels appear in the accept, tune, silence
order; a check whose tune sub-section states none applies still prints the tune
label; a value wider than its column is elided rather than wrapped, asserted by
checking no output line exceeds the given width; with `color_enabled` false the
output contains no ESC byte; with `ascii_glyphs` true the output contains the
ASCII status words and none of the symbol glyphs; and a fixed model at a fixed
width matches a golden through `check_golden`.
