<objective>
Build the fail-first machinery before the semantics that must satisfy it: a
test-only check registry, a stub measurement source, a coverage gate that fails
when any registered semantic lacks a fixture for a status it can emit, a
permanent canary that must always report failing, and the golden and determinism
harnesses every later report plan depends on.

Purpose: Phase 1 shipped six checks structurally incapable of observing their own
subject. This plan is the direct counter (D-14 through D-17) and it is built as
infrastructure, not retrofitted after the fact.
Output: a coverage gate, a canary, a golden harness, a determinism harness, and a
`cli_harness.h` that cannot silently truncate what it captures.
</objective>

  <action>
Build the two gates that make the discipline mechanical rather than aspirational.

Coverage gate — `tests/unit/test_fail_first_coverage.cpp`, tag `[failfirst]`.
Declare, in code, a table mapping each `Semantic` to the set of `Status` values
it can legitimately emit: `exact` emits pass/fail/error; `tol` emits
pass/info/warn/fail/error; `set` emits pass/fail/error; `presence` emits
pass/fail/error; `hash` emits pass/fail/skipped/error; `dist` emits
pass/warn/fail/error; `span` emits pass/info/fail/error. Every semantic emits
`error` because a `value_kind` mismatch is an error (D-09), and `hash` is the one
that must be able to emit `skipped` — proving that is as load-bearing as proving
it can fail, because a semantic that can never say "we cannot tell" converts
uncertainty into a verdict (ENG-14).

For each `(semantic, status)` cell the table declares, require at least one
fixture pair under `tests/fixtures/snapshots/` whose name follows
`<check_id>__<status>.{a,b}.snap.json`, run it through `compare_fingerprints`
against `test_registry()`, and assert the resulting finding carries exactly that
status. A missing fixture is a test failure whose message names the specific
`(semantic, status)` cell that is uncovered — not a skip and not a silent pass.
Seed only the cells whose semantic is already implemented (`exact` at this
point); the gate must therefore also assert that every cell for an implemented
semantic is covered, and record the remaining semantics as expected-uncovered in
a checked-in allow list keyed by semantic. Plan 02-04 removes entries from that
allow list as it implements each semantic; a semantic that is implemented but
still listed is itself a failure, so the allow list cannot rot silently.

Canary — `tests/unit/test_canary.cpp`, tag `[canary]`. Hand-author
`tests/fixtures/snapshots/canary_{a,b}.snap.json` as a deliberately-divergent
pair on a `fail`-severity test check. The test asserts the comparison produces
exactly one finding, that its status is `fail`, and that its check ID is the
expected one. If this pair ever comes back clean the harness is broken rather
than the fixture, which is precisely the failure a green suite otherwise hides.
Add a comment in the fixture files stating that they are intentionally wrong and
must never be "fixed".

Add both files to `add_executable(mediadiff_unit_tests ...)`.

Record the discipline as a project convention, not only as this phase's gate
(D-17). Append a Conventions entry to `.planning/PROJECT.md` stating that every
comparison semantic and every registered check must declare one fixture pair that
triggers it and one that comes back clean, that the unit is the semantic crossed
with each status it can emit rather than merely pass versus fail, and that the
permanent canary fixture must always report failing. Phases 3 through 7 add
roughly sixty real checks and docs 02 to 06 already require a triggering pair and
a clean pair for each; writing the rule down where those phases inherit it is what
lets the verifier check for it rather than hope for it.
  </action>

  <action>
Close the capture defects first, because every later report test asserts against
what this harness captures. In `tests/integration/cli_harness.h`, POSIX branch:
retry `read()` when it returns -1 with `errno == EINTR` instead of treating the
result as end of stream — the current code closes the pipe and marks it done,
which silently truncates captured output and lets an assertion pass against
incomplete data; close both pipe descriptors on the `select()` error path before
breaking out of the loop, so an error does not leak two descriptors per spawn;
and check `waitpid`'s return value, retrying on `EINTR` and recording an
`exit_code` of -1 when it genuinely fails, so a wait failure is not read as a
successful exit. Leave the Windows branch behaviourally unchanged. Add a test
that spawns a command producing more than one pipe buffer of output (larger than
64 KiB on both streams) and asserts the captured length is exactly what was
produced, so the truncation path has an actual observer.

Golden harness — `tests/support/golden.{h,cpp}` exposing
`void check_golden(std::string_view case_name, std::string_view actual)`. It
resolves `tests/golden/<case_name>.txt` through `fixture_paths.h`. When the
environment variable `UPDATE_GOLDENS` is set to a non-empty value it writes
`actual` to that path and passes; otherwise it compares byte-for-byte and, on
mismatch, fails with a unified-diff-style message showing the first differing
line and its offset. A missing golden file when `UPDATE_GOLDENS` is not set is a
failure, never an implicit create — otherwise the first run of a broken renderer
would mint its own output as the expected answer. Write `tests/golden/README.md`
stating that goldens are refreshed locally with `UPDATE_GOLDENS=1 ctest ...`, that
the refresh must appear as a reviewable diff in the pull request, and that CI
never sets the variable (D-12).

`[integration]`, named to match the existing `<slug> - <REQ-ID>: <behavior>`
convention. It runs the same `compare ... --json` invocation twice through
`run_cli` and asserts the two captured stdout strings are byte-identical
(D-13, TRUST-05). Assert on the full captured string, not a hash and not a length.

Add the new files to the relevant `add_executable` lists and link
`tests/support/golden.cpp` into both test targets.
