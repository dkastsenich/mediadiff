<objective>
Close gap **G-02-4**: make the byte-wise-order fixture in `tests/unit/test_dir_pairing.cpp` portable to a case-insensitive filesystem **without weakening what it asserts**, ending the single failure that stopped `build (arm64-osx)` at 296 of 297; and install a permanent scan gate so the same case-collision assumption cannot recur anywhere in the test tree.

Purpose: `build (arm64-osx)` is a required status check on the active `main merge gate` ruleset. macOS ships APFS case-insensitive by default, so the fixture's `"Beta.snap.json"` and its lowercase twin denote one file — `write_file()` overwrote, four files landed on disk, and `REQUIRE(result->size() == names.size())` compared 4 against 5. Catch2's `assertions: 2 | 1 passed | 1 failed` pins the failure to the count, not the order: the test never reached its ordering check.

**The product is not at fault and must not be touched.** `src/cli/dir_pairing.cpp` keys pairing on `std::map<std::string, FilePair>`, ordered by `std::string::operator<` — byte-wise, locale-independent, and with no reliance on `directory_iterator` order. DIR-04's byte-wise ordering guarantee holds on macOS; the test simply never got far enough to check it. This is a fixture-portability defect, not a determinism defect.

Output: one fixture whose five names are distinct under case folding, an explicit literal expected order that makes the byte-boundary claim auditable from the test source, a self-proving assertion that the fixture still discriminates byte-wise order from case-folded order, and one new lint script.

**Honesty about verification.** APFS cannot be mounted on this Linux host and case-insensitivity cannot be simulated in a way that would exercise `write_file()` the way macOS does. What is locally provable is the whole of the source-level invariant — that no two names collide under case folding, that the expected order is byte-wise correct, and that the fixture still has teeth — plus that all 11 `unit.dir_pairing` tests pass on Linux. Only a pushed CI run can prove the macOS leg goes green. Plan `02-16-PLAN.md` owns that read.

**Confidence here is higher than on the Windows leg, and the plan says so deliberately.** This was the only failure among 297 tests on macOS: the suite ran end to end, so there is no large unexecuted remainder hiding behind it. That asymmetry is real and should not be flattened into the Windows leg's much weaker position.
</objective>

Work only inside the `TEST_CASE` named `dir_pairing: the returned order is byte-wise sorted` (currently lines 97-117). Leave the other ten test cases, `unique_scratch_dir` and `write_file` alone.

**1. Replace the colliding name.** The fixture's five-element `names` vector currently holds, in this order, a `zeta` stem, an `alpha` stem, a `Beta` stem, a lowercase twin of that `Beta` stem, and a `1` stem — all with the `.snap.json` suffix. Keep four of them exactly as they are. Replace **only the lowercase twin of the `Beta` stem** with the stem `Zulu`, giving `"Zulu.snap.json"`. Do not reorder the vector; the fixture is deliberately not in sorted order, which is what makes the ordering assertion meaningful.

Why `Zulu` specifically, stated so the choice is auditable from this plan alone. The five first bytes become `'1'` = 0x31, `'B'` = 0x42, `'Z'` = 0x5A, `'a'` = 0x61, `'z'` = 0x7A. The ASCII uppercase block ends at 0x5A and the lowercase block begins at 0x61, so `Beta` and `Zulu` both sit below every lowercase stem byte-wise while `alpha` and `zeta` sit above — the straddle the original case pair existed to exercise, now carried by two distinct stems instead of one name written twice. Case-folded, the five lower forms are `1`, `alpha`, `beta`, `zeta`, `zulu`: all pairwise distinct, so five files land on APFS and NTFS exactly as they do on ext4. And the two orders genuinely disagree — byte-wise the order is `1`, `Beta`, `Zulu`, `alpha`, `zeta` while case-folded it is `1`, `alpha`, `Beta`, `zeta`, `Zulu`, differing in three of five positions. The original fixture's discriminating power is not merely preserved, it is doubled: `Zulu` moves from last to third under the byte-wise rule.

**2. Keep the size assertion exactly as it is.** `REQUIRE(result.has_value())` and `REQUIRE(result->size() == names.size())` stay unmodified. That second line is the assertion that caught this defect; it is the collision detector and it must survive intact.

**3. Replace the self-derived expected order with an explicit literal.** Today the test builds `expected_order` by copying `actual_order` and sorting it, then compares the two. That form can only ever detect "the result is not sorted"; it records nothing about *which* byte-boundary property the straddling stems exist to prove, and a reader cannot audit the intended order from the source. Replace it with a `const std::vector<std::string>` holding the five names as literals in byte-wise order — the `1` stem, then `Beta`, then `Zulu`, then `alpha`, then `zeta`, each with the `.snap.json` suffix — and `CHECK(actual_order == expected_order)` against that. This is strictly stronger: it asserts the exact order, not merely sortedness.

**4. Add the teeth assertion.** Make a copy of the expected order and sort the copy with a comparator that compares case-folded: a `std::lexicographical_compare` over the two strings using an element comparator that applies `std::tolower` to each `char` cast through `unsigned char` (the cast is required — passing a possibly-negative `char` to `std::tolower` is undefined, and `-Wall -Wextra -Werror` is on this target). Then `CHECK` that the case-folded order is **not equal** to the expected order. This is what converts "the fixture has teeth" from an author's claim into a test-enforced invariant: a future editor who replaces these names with a set whose byte-wise and case-folded orders coincide gets a failing test rather than a silently de-fanged one. Add `<cctype>` to the standard-include block in alphabetical position after `<atomic>`; `<algorithm>` is already included and supplies both `std::sort` and `std::lexicographical_compare`.

**5. Comment the hazard at the point of use**, in the file's existing explanatory register, covering three things: that macOS ships APFS case-insensitive by default so two fixture names differing only by ASCII case denote one file and `write_file`'s truncating open silently overwrites rather than adding, which is what made the size assertion read 4 against 5 in CI run 31943688186; that the uppercase stems are chosen to straddle the ASCII case boundary (0x5A / 0x61) so the byte-wise order provably differs from a case-folded one, which is the property DIR-04 rests on; and that `scripts/lint_fixture_case_collisions.sh` (Task 2) now enforces the no-collision rule across the whole test tree. Write the comment describing the *stems* and the byte values — do NOT write the removed lowercase filename literal into the comment, because Task 1's gate greps the file for its absence and a comment mentioning it would fail that gate for no reason.

This exact change — the `Zulu` substitution, the literal expected order, the case-folded comparator and the `<cctype>` include — was compiled ahead of planning against the real TU with `-O3 -DNDEBUG -std=c++20 -Wall -Wextra -Werror` and produced zero diagnostics. If a warning appears, it is new information; do not resolve it by removing the `unsigned char` cast.

  <action>
Write a new bash lint, `scripts/lint_fixture_case_collisions.sh`, whose single charter is: **within any one test source file, no two filename-shaped string literals may be equal after ASCII case folding while differing byte-wise.** That is precisely the assumption that made a five-name fixture write four files on APFS, and the user's own gap diagnosis asks for it to be audited across every test that writes files by name rather than fixed in one place.

Scan target: the `tests` directory, restricted to `*.cpp` and `*.h`. Follow `lint_check_id_strings.sh`'s guard exactly — if `tests` does not exist, or if the file enumeration yields zero files, print a diagnostic to stderr and exit 1.

Literal shape to extract: a double-quoted token beginning with an alphanumeric or underscore, continuing over alphanumerics, underscore, period, plus and hyphen, and containing at least one period followed by a further alphanumeric run. This deliberately matches `alpha.snap.json`, `not_a_dir.txt`, `report-1.0.json` and `checks.def` while ignoring prose strings, format strings and paths with slashes. Extract per file, deduplicate, then group by the ASCII-lowercased form. Any group holding more than one distinct original form is a violation: print the file and both spellings.

Fold case with `tr '[:upper:]' '[:lower:]'` or an equivalent that is explicitly ASCII-only. Do not use a locale-sensitive fold — the property being checked is what a case-insensitive filesystem does to ASCII names, and a locale-dependent gate that behaves differently on the runner than on a developer machine would be its own portability defect.

Per-file opt-out for the legitimate case — two case-variant names written deliberately into *different* directories, which is portable and not a defect. A file containing a marker comment of the form `fixture-case-allow:` followed by a reason is skipped, and the script prints which files it skipped and why, so an opt-out is visible in the gate's own output rather than silent. Require the reason: a bare marker with nothing after it does not count as an opt-out and the file is still scanned. No file in the tree needs this marker today; it exists so the correct response to a future false positive is a one-line documented exemption rather than deleting the gate.

**Self-test control clause, run before the real scan on every invocation.** Materialise a synthetic known-bad fixture in a temporary file containing two filename literals that differ only by the case of their first letter, run the identical matcher against it, and exit 1 with a distinct diagnostic if the matcher does NOT flag it. Clean up with a trap. This is the same discipline `02-13-PLAN.md` used as an inline control clause, promoted into the gate itself: a matcher that silently stops matching reports "clean" forever, and G-02-2's own root cause was a verification that had only ever been run one way.

Document, in a "Known limitation (stated deliberately, not hidden)" paragraph matching the two existing lints' register: this is a line-based literal scan, not a tokenizer or a dataflow analysis, so it cannot tell whether two colliding names are actually written into the same directory (it is deliberately conservative and flags them regardless, which is what the opt-out marker is for); it will not catch a filename assembled at runtime by concatenation; and it does not model Unicode case folding, only ASCII, which is the boundary APFS and NTFS actually apply to the names this suite uses.

Record in the header comment what this gate defends: `build (arm64-osx)` is a required status check, macOS ships APFS case-insensitive by default, and a fixture whose names collide there writes fewer files than it names — which surfaces as an off-by-one count assertion far from its cause, exactly as it did in CI run 31943688186. Note also that a pre-authoring scan of the whole test tree found exactly one collision (the one Task 1 removes) and nothing else, so this gate starts clean and its job is to keep it that way.

Do not add an execute bit expectation — the existing lint steps invoke `bash scripts/<name>.sh`, and `02-16-PLAN.md` wires this one the same way. Do not wire it into `.github/workflows/ci.yml` here; that file belongs to `02-16-PLAN.md` and touching it from two wave-1 plans would collide.
