  <name>Task 1: Make the ctest count parse dialect-independent</name>
  <precondition>GNU sed is on PATH — `sed --version` reports GNU sed — because this task's verification uses the `--posix` dialect switch, which is a GNU feature and is the only way to execute the BSD failure mode from a Linux host. A configured build tree at `build/x64-linux` also exists, so `ctest --test-dir build/x64-linux -N` prints a real `Total Tests:` line to parse against.</precondition>
  <files>.github/workflows/ci.yml</files>
  <action>
At line 246, change the bracket-expression quantifier in the sed substitution that captures CTest's count so it uses a digit followed by zero-or-more digits instead of the GNU-only one-or-more backslash quantifier. Everything else on the line stays exactly as it is: the `sed -n` invocation, the `^Total Tests: ` anchor, the `$` terminator, the `\1` replacement, the `p` flag, and the trailing `|| true`.

Use the bracket-repetition form, NOT `sed -E`. Both work under GNU and BSD sed, but `-E` adds an assumption that the flag is supported for no benefit, and the substitution is the only thing that needs to change.

Preserve the guard's two branches untouched. The empty-capture branch and the zero-count branch are distinct and must stay distinct: with the portable pattern, a genuinely empty suite still captures the string `0`, which is non-empty, so control falls through the emptiness check and reaches the zero check, which fires with its own specific "a green run that executed nothing is a false pass" diagnostic. Loosening or deleting either branch would trade a false FAIL for the false PASS the guard exists to prevent — do neither.

Add a paragraph to the existing comment block above the line, in its established register, recording all three of these:

- This pipeline runs under BSD sed on the macOS legs. The workflow sets a bash default shell, so the Windows leg runs Git Bash and gets GNU sed, and Linux gets GNU sed — macOS is the only host in the matrix whose `/usr/bin/sed` is BSD. GNU-only regex extensions must therefore never appear here.
- Name the specific trap: BSD sed reads a backslash-quantifier as a literal character rather than as a repetition operator, so a pattern using it does not merely mis-count — it matches nothing at all, `sed -n` prints nothing and exits 0, and neither `|| true` nor `pipefail` intervenes. The capture comes back empty and the step aborts before any test runs.
- Why a comment is warranted rather than trusting care: the commit that introduced this defect carried its own note claiming the line had been verified — a GNU-sed-only verification, which is precisely how the defect shipped. A verification that only ever ran on one dialect is what a note at this line has to guard against.

Do not touch anything else in the workflow. A whole-file scan already confirmed this is the only GNU-only regex construct under `.github/workflows/` — there is no sibling landmine to chase, and the verification below re-asserts that.
  </action>
  <verify>
    <automated>test -z "$(printf 'Total Tests: 296\n' | sed --posix -n 's/^Total Tests: \([0-9]\+\)$/\1/p')" && POSIX_COUNT=$(ctest --test-dir build/x64-linux -N | sed --posix -n 's/^Total Tests: \([0-9][0-9]*\)$/\1/p') && GNU_COUNT=$(ctest --test-dir build/x64-linux -N | sed -n 's/^Total Tests: \([0-9][0-9]*\)$/\1/p') && test -n "$POSIX_COUNT" && test "$POSIX_COUNT" = "$GNU_COUNT" && test "$POSIX_COUNT" -gt 0 && test "$(printf 'Total Tests: 0\n' | sed --posix -n 's/^Total Tests: \([0-9][0-9]*\)$/\1/p')" = "0" && test "$(grep -rF '\+' .github/workflows/ | wc -l)" -eq 0 && grep -qF 's/^Total Tests: \([0-9][0-9]*\)$/\1/p' .github/workflows/ci.yml</automated>
  </verify>
