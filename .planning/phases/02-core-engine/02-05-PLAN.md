<objective>
Ship the five profiles, make severity and tolerance resolve from the `checks.def`
baseline through the selected profile with the provenance recorded, keep
`volatile` checks computed but non-gating, and make the `transform` profile
compare against a declared expectation instead of the baseline.

Purpose: the profile is the single knob that decides whether a real pipeline's
normal variation is a regression. Getting `sw-encoder` right as the default is
what makes "a no-change re-run is clean out of the box" true.
Output: `Policy` resolves through profile in a deterministic single pass, and
each profile's behaviour is asserted rather than assumed.
</objective>

  <action>
Make the `volatile` flag behave as doc 01 section 4 specifies, and make the
distinction between "not computed" and "computed but ignored" observable.

In `resolve_policy`, a check whose `CheckDef::is_volatile` is true resolves to
`Severity::ignore` in every one of the five profiles, and that resolution is
recorded in the provenance chain as a `builtin` entry naming the volatile flag as
the reason. A profile that declares no override for a volatile check does not
promote it; only an explicit later-layer override can, which is why the flag is
applied at the `builtin` layer rather than as a post-pass that would sit above
config and CLI.

In `compare_fingerprints`, a check resolving to `Severity::ignore` is still
compared and still produces a `Finding` carrying its real `Status`, its baseline
and candidate values, and its delta. The finding is marked as non-gating so no
exit code derives from it, and the report layer decides whether to display it —
by default it is hidden and under `-v` it is shown. The engine never drops it,
because "trust never requires faith": a value the tool declined to gate on is
still a value the user is entitled to see.

`tests/unit/test_volatile.cpp`, tag `[volatile]`: `t.volatile_tag` with equal
values yields a finding whose `status` is `pass`; with differing values it yields
a finding that exists, whose `status` reflects the real difference, whose
resolved `severity` is `ignore`, and which does not contribute to the worst
severity used for the exit code; resolving `t.volatile_tag` under all five
profiles yields `ignore` in each; and an explicit later-layer override to `fail`
does gate — construct that override by appending a `cli` provenance layer
directly through the policy API rather than by parsing argv, since argv handling
is plan 02-06's subject.

  <action>
Add the expectation mechanism the `transform` profile needs, scoped to
`expect.resolution` only — `expect.frame_rate` is v2 (EXT-04) and must not be
built here.

`struct TransformExpectation { std::optional<std::string> resolution; };` lives
beside `Policy` and is carried on it. Parse the declared value in one place:
`mediadiff::expected<ResolutionExpectation, Error> parse_resolution_expectation(std::string_view)`
accepting either a scale factor written as a positive integer or decimal followed
by `x` (for example `2x`, `1.5x`) or an absolute `WIDTHxHEIGHT` pair (for example
`3840x2160`). A scale factor is stored as an exact rational, never a double.
Anything else is `ErrorKind::usage` with a message naming both accepted forms.
The TOML source of this block is read in plan 02-06; this task provides the
parser and the comparison behaviour, and the unit tests construct the expectation
directly.

Mark in `checks.def` which checks are expectation-affected by adding an optional
`transform_affected = true` key to a check record, and have the generator carry
it into `CheckDef`. Only a check carrying that flag changes behaviour; every
other check compares normally under `transform`, so the profile does not silently
alter the whole registry. In Phase 2 no shipped check carries it — the resolution
identity check lands in Phase 4 — so set it on a test-only check in
`tests/support/test_checks.def` and note in `checks.def` that the flag exists and
is unused by shipped checks until then.

In `compare_exact`, when the policy's profile is `transform`, the check carries
`transform_affected`, and the policy holds a resolution expectation, compare the
candidate against the value the expectation derives from the baseline rather than
against the baseline itself: for a scale factor, multiply the baseline's parsed
dimensions by the exact rational and require an exact integer result, failing with
a message naming the derived expectation when it is not; for an absolute pair,
compare the candidate against that pair directly. In every other configuration
the comparator's behaviour is unchanged, so the transform path is additive.

`tests/unit/test_transform_profile.cpp`, tag `[transform]`: `2x` applied to a
`1920x1080` baseline expects `3840x2160` and passes when the candidate matches;
the same setup fails when the candidate is `3840x2159`, with the message naming
the derived expectation; an absolute `3840x2160` expectation passes regardless of
the baseline value; a malformed expectation string is `ErrorKind::usage` naming
both accepted forms; a scale factor of `1.5x` against `1920x1080` derives
`2880x1620` exactly; a scale factor that would derive a non-integer dimension is
a usage error rather than a rounded pass; and a check without
`transform_affected` compares by baseline equality even under `transform`.
  </action>

| T-2-18 | Tampering | `src/core/profiles.cpp` | medium | mitigate | `profile_from_string` matches the five canonical spellings exactly, with no prefix matching and no case folding, so a near-miss profile name is a usage error rather than a silent selection of a laxer policy than the user asked for. |
