<objective>
Complete the configuration precedence chain — profile, then `[severity]` and
`[tolerance]`, then matching `[override.*]` blocks in file order, then CLI
`--set`/`--tol` in argv order — with the winning layer recorded per value, and
expose the result through `list-checks --effective` so a user can see exactly
what was applied.

Purpose: doc 01 calls this "auditable policy". A merge whose outcome cannot be
inspected is a config surprise waiting to happen, and a config surprise on a
gating tool reads to the user as a false positive.
Output: `mediadiff.toml` is loaded once, merged deterministically, and dumped on
demand with the resolved chain visible under `-v`.
</objective>

`struct ConfigFile { std::optional<std::string> profile; std::vector<GlobRule> severity; std::vector<GlobRule> tolerance; std::optional<TransformBlock> transform; std::optional<DirBlock> dir; std::vector<OverrideBlock> overrides; std::string source_path; };`
where `struct GlobRule { std::string glob; std::string value; int file_order; };`
preserves the position each entry appeared at, because doc 01 section 6 resolves
`[override.*]` blocks and glob rules in file order and that order must survive
into the provenance chain.

`mediadiff::expected<std::optional<ConfigFile>, Error> discover_and_load(std::optional<std::string> explicit_path)`
implements the discovery order: an explicit `--config` path, else `./mediadiff.toml`,
else no config at all. An explicit path that does not open is
`ErrorKind::input_open`; a missing `./mediadiff.toml` is not an error and yields
`std::nullopt`. Open through `fopen_utf8`, read the bytes, and hand them to
tomlplusplus's string-parsing entry point rather than its file-path one, so path
encoding stays inside `util/fs.h` on Windows.

After tomlplusplus reports a successful parse, validate the shape before use, and
map every violation to `ErrorKind::usage` carrying a message naming the offending
key and its position: an unknown top-level section; a `[severity]` value that is
not one of `ignore`, `info`, `warn`, `fail`; a `[tolerance]` value that
`parse_tolerance` rejects for the check the glob resolves to; a `profile=` value
`profile_from_string` rejects; a glob that `glob_matches` reports as malformed;
and a value of the wrong TOML type for its key. A parse failure from tomlplusplus
itself is also `ErrorKind::usage`, carrying the library's own line and column —
never a crash and never a silent fallback to defaults.

`[override."<glob-on-relative-path>"]` blocks are captured with their path glob
and their inner `[severity]`/`[tolerance]` tables, in file order. They apply only
in `dir` mode (plan 02-11 consumes them); loading and validating them here means a
typo in an override block is reported the moment the config is read, not on the
one run that happens to use `dir`.

Extend `resolve_policy` from two layers to four, keeping it a sequence of passes
over the same `Policy::per_check` vector so the final signature is
`mediadiff::expected<Policy, Error> resolve_policy(const CheckRegistry&, ProfileId, const std::optional<ConfigFile>&, std::span<const CliOverride>)`.

Layer 3 applies `[severity]` and `[tolerance]` rules in ascending `file_order`,
expanding each glob through `glob_select` and writing to every matched index, then
applies matching `[override.*]` blocks in file order the same way. Layer 4
applies the CLI overrides in the order they appear in the span. Each write
appends a `PolicyProvenance` entry naming the layer, the source detail (the glob
plus its file position, or the argv text) and the value written; nothing is ever
overwritten in the chain, so the full history is recoverable. Last writer wins by
construction, because a later pass writes over an earlier one's value while
appending to its chain.

`struct CliOverride { enum class Dimension { severity, tolerance }; Dimension dimension; std::string glob; std::string value; std::size_t argv_index; };`
Severity and tolerance are independent dimensions written to different fields of
`ResolvedCheck`, so interleaving `--set` and `--tol` in argv cannot change the
result of either; only the relative order within a dimension matters.

`src/cli/options.{h,cpp}` owns the argv capture and nothing else. It binds
`--set` and `--tol` to `std::vector<std::string>` options — CLI11 accumulates a
container option in encounter order without `take_all()`, which is for a
different case — and converts each accumulated string into a `CliOverride`,
assigning `argv_index` from a monotonically increasing counter within each
dimension. Malformed override text (no `=`, an empty glob, an empty value, or a
severity word outside the four) is `ErrorKind::usage` naming the offending
argument. A `--tol` value that `parse_tolerance` rejects for the check its glob
resolves to is `ErrorKind::usage` naming the expected unit, which is where CLI-10
becomes reachable from the command line.

Load the config exactly once, in the command entry point, before any other work;
pass the resolved `Policy` by const reference from there on. The `Policy` type is
immutable after `resolve_policy` returns — expose no non-const accessor to
`per_check` — so a future `dir` worker cannot mutate it.

`void register_list_checks_command(CLI::App&)` adds `list-checks` with flags
`--effective`, `--profile`, `--config`, `--set`, `--tol` and `-v`. Without
`--effective` it prints the registry: one line per check with its ID, group,
semantic, unit, value kind and baseline severity, in registry declaration order.
With `--effective` it resolves the full policy through the same
`resolve_policy` call `compare` uses — not a parallel reimplementation — and
prints one row per registered check with the resolved severity and tolerance.
Row count equals `registry.size()` in both modes, so a check can be neither
duplicated nor omitted, and with no config and no overrides the table is fully
populated with built-in values rather than empty.

The provenance renderer (ENG-06, ROADMAP success criterion 2). The phase's second
success criterion requires "the resolved severity chain visible under `-v`". That
chain is `ResolvedCheck::chain`, a `std::vector<PolicyProvenance>` built by plan
02-05 and extended by Task 2; `PolicyProvenance` has exactly three fields —
`layer`, `detail`, `value` — and **all three are rendered**. Because three
separate surfaces must show the same chain, the formatting lives in one place:

Create `src/cli/provenance_render.{h,cpp}` exposing
`std::string render_provenance_chain(std::span<const PolicyProvenance>, int indent_spaces)`.
It emits one line per chain entry, in chain order — which is resolution order,
because every layer appends and none rewrites — with no sorting, no reversal, no
deduplication and no filtering, so a layer that wrote a value the next layer
replaced is still visible. Each line is: `indent_spaces` spaces, then the layer
name from the closed set `builtin`, `profile`, `config`, `cli` left-padded to a
fixed width (the longest spelling is `profile`, seven characters), then the value
that layer wrote, then the source detail in parentheses. Worked shape for a check
whose built-in `warn` was zeroed by a profile, restored by config and finally
forced by an argument:

```
  builtin  warn    (checks.def default)
  profile  ignore  (profile sw-encoder)
  config   warn    (mediadiff.toml [severity] entry 2, glob meta.*)
  cli      fail    (--set meta.*=fail, argv position 4)
```

The last line is the resolved value by construction — last writer wins — so no
winner marker glyph is emitted. That keeps the chain text identical under
`--ascii`, `--no-color` and a non-TTY stdout, which is what lets `list-checks`
goldens stay byte-stable. `detail` is whatever the writing layer recorded in
Task 2 (the glob plus its file position, or the argv text plus its index);
this renderer neither invents nor abbreviates it. Rendering happens in
`src/cli/`; `PolicyProvenance` carries data and formats nothing (ENG-16).

The three `-v` surfaces that show the chain, and who implements each:

| Surface | Form | Implemented in |
|---|---|---|
| `list-checks --effective -v` | `render_provenance_chain` output, indent 2, printed under each check's row | this task |
| `compare --json -v` | the same three fields as a JSON array `severity_chain`, one object per entry with keys `layer`, `detail`, `value`, in the same chain order — structured, not the text renderer | plan 02-08 Task 1 |
| `inspect -v` | `render_provenance_chain` output, indent 4, printed under each rendered measurement's check | plan 02-10 Task 3 |

Under `-v`, `list-checks --effective` therefore follows each row with that
check's chain lines. Without `-v` no chain line is printed at all, so the two
modes are distinguishable by line count alone.
