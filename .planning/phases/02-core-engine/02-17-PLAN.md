<objective>
Make mediadiff's bytes the same on every platform, at both ends: the bytes git puts on disk at checkout, and the bytes the binary writes to a redirected stdout. These are two halves of one property and they must land together.

Purpose: `G-02-5` asks whether mediadiff's byte-level output is identical on Windows and POSIX. Round 3's evidence says it is not, in two independent places — and one of those two is a genuine product defect against a hard project constraint (byte-identical `--json`), not a test-portability wrinkle.

Output: `.gitattributes`, one Windows-only call in `wmain`, and one test that can see the defect if it ever comes back.

## The evidence, and where this plan departs from the gap record's grouping

`02-UAT.md`'s `G-02-5` groups four failing tests (#95, #67, #75, #201) under one cause and records lead B (stdout may be text-mode) as **not confirmed**, needing "either a Windows console run or a new test". It is confirmed already, by evidence that was in run 31946964023 the whole time. Reading the seven golden call sites in this repository shows a 7-of-7 correlation:

| Golden case | Call site | How "actual" is produced | Result on Windows, run 31946964023 |
|---|---|---|---|
| `junit_basic` | `tests/unit/test_junit.cpp:219` | in-process render into `rendered` | **FAILED (#67)** |
| `markdown_basic` | `tests/unit/test_markdown_budget.cpp:226` | in-process render into `rendered` | **FAILED (#75)** |
| `tty_basic` | `tests/unit/test_tty_render.cpp:258` | in-process render into `rendered` | **FAILED (#201)** |

| `list_checks_effective` | `tests/integration/test_list_checks.cpp:91` | `run_cli(...).out` | passed |

Every golden whose "actual" is rendered in-process failed. Every golden whose "actual" came out of a spawned `mediadiff.exe` passed. Both groups read the SAME golden files through the SAME code path (`tests/support/golden.cpp:89`, `fopen_utf8(path, "rb")` — binary, no translation). The expected side is therefore identical for all seven, which leaves the actual side as the only variable. The only reading that fits is:

- the goldens on disk are **CRLF** (no `.gitattributes` exists; `git check-attr text eol` returns `unspecified` for every golden; GitHub's Windows runners default `core.autocrlf=true`), and
- the spawned binary's stdout is **also CRLF**, because the MSVC CRT opens fd 1 in `_O_TEXT` and `grep -rn '_setmode\|_O_BINARY\|O_BINARY' src/` returns zero matches.

CRLF matched CRLF, so four tests passed for the wrong reason. LF-in-memory met CRLF-on-disk, so three failed.

**This changes the plan shape in a way the round's brief did not anticipate, and the departure is stated here deliberately.** The brief asks for `.gitattributes` to land alone first as the cheap high-certainty tracer. It cannot: on its own it pins the disk side to LF while stdout keeps translating, converting three failing golden tests into four *different* failing golden tests. Cheapest-first is honoured — this is still the smallest change that proves the whole byte-identity path end to end, and it lands and is read before anything speculative — but the smallest *safe* slice is two files, not one.

Two further consequences follow, and both are used below rather than re-derived:

1. **`#247` is downstream, exactly as `G-02-7` suspected.** `tests/integration/test_explain_inspect.cpp:28`'s `split_lines` uses `std::getline` on `'\n'` only, so a CRLF stdout leaves `"meta:\r"` in `lines[i]` and `lines[i] == "meta:"` is false. That file is NOT modified by this plan. If it passes on Windows after this change, it was never its own defect.
2. **`#95` is NOT part of this cause and is not this plan's work.** Its child process is `MEDIADIFF_PYTHON`, and the 2500-byte delta comes from Python's own text-mode `sys.stdout`. `tests/process_spawn.h`'s Windows reader uses raw `CreatePipe` + `ReadFile` and performs no translation. `02-18-PLAN.md` owns it.
