<objective>
Guarantee a Python >= 3.11 interpreter on every CI build-matrix leg by adding a single
`actions/setup-python` step to the `build` job.

Purpose: Phase 2 adds `tools/gen_registry.py`, which parses `src/core/checks.def` using stdlib

whatever interpreter each runner image happens to ship — unpinned and unverified.

Output: One inserted step in `.github/workflows/ci.yml`. No other file changes.

Explicitly NOT in scope: wiring the generator into `CMakeLists.txt` (it lands in Phase 2 plans
02-01/02-02 and does not exist yet), any Python-version assertion step, any `tomllib` import smoke
test, any new job, and any edit to the `lint` job, `strategy.matrix`, `permissions`, or any other
step. This task only guarantees the interpreter is present.

    Insert one step into the `build` job's `steps:` list, positioned strictly after the
    `Initialise MSVC x64 developer environment (Windows)` step and strictly before
    `Install nasm (Linux)`. Indent it to match its siblings (6 spaces to the `-`, 8 to the keys).

    The step must have: a `name` describing that it pins the interpreter for the Phase 2 registry
    generator; `uses: actions/setup-python@v6`; and a `with:` block whose sole key is
    `python-version` set to the quoted string `'3.11'`.

    Three properties of this step are load-bearing and must each be satisfied deliberately:

    1. **No conditional key.** Unlike its immediate neighbours, this step is deliberately
       unguarded — every neighbouring step in this region is OS-scoped, so the natural reflex when
       editing here is to add a matching guard. Do not. The generator runs on all five matrix legs
       (`x64-linux`, `arm64-linux`, `x64-windows-static-md`, `x64-osx`, `arm64-osx`), so the
       interpreter must be provisioned on all five. The step's `with:` block is its only child
       mapping besides `uses`/`name`.

    2. **Tag pin, not SHA.** Per the file's convention, first-party actions use a tag. Use the
       major-version tag `v6` — not a full SHA, and not a patch-level tag.

    3. **Quoted version string.** `'3.11'` must be quoted. Unquoted, YAML parses it as a float,
       which silently truncates a value like 3.10 to 3.1; quoting is the file-wide safe form and
       is what the acceptance check asserts. The bare `'3.11'` series pin (rather than `'3.x'`)
       resolves to the latest 3.11.x on every runner image, which both clears the `tomllib` floor
       and keeps the interpreter deterministic across the 5 legs.

    **Why `v6` and not `v7`:** `actions/setup-python@v7.0.0` was published 2026-07-20, roughly four
    weeks before this task. This project already applied exactly this maturity discipline once —
    FFmpeg was pinned to 8.1 rather than the then-8-days-old 9.0 (decision recorded in PROJECT.md
    per BUILD-10), and `windows-2022` was pinned explicitly rather than floating on
    `windows-latest`. `v6.0.0` (2025-09-04) is eleven months mature, runs on Node 24 — so it emits
    none of the Node 20 deprecation warnings `v5` now produces — and requires runner >= 2.327.1,
    which every current GitHub-hosted image exceeds. If a later maintainer bumps to `v7`, that is a
    deliberate bump, not a default.

    Add a short comment above the step recording why the interpreter is pinned (stdlib `tomllib`
    floor for the Phase 2 registry generator) and why it carries no OS guard, matching the file's
    existing habit of explaining non-obvious CI decisions inline. Keep it to a few lines — the
    surrounding comments are long because they encode expensive debugging history; this step has
    none yet.

    Change nothing else. The diff must be pure insertion: zero deleted lines.
  </action>
