# Quick Task 260814-js4 — MSVC on Windows, Release build type

Two correctness defects found by CI run `31787938349` (the first run to get past configure).
Both produce a build that is wrong rather than broken, which is why neither surfaced earlier.

## Defect 1 — Windows builds with MinGW GCC, not MSVC (BLOCKING)

Evidence from the Windows leg's Build step:

```
C:/mingw64/bin/../lib/gcc/x86_64-w64-mingw32/14.2.0/../../../../x86_64-w64-mingw32/bin/ld.exe:
  vcpkg_installed/x64-windows-static-md/debug/lib/Catch2d.lib(...): undefined reference to `__CxxFrameHandler4'
  ... undefined reference to `__GSHandlerCheck_EH4'
collect2.exe: error: ld returned 1 exit status
```

`__CxxFrameHandler4` and `__GSHandlerCheck_EH4` are MSVC's C++ exception-handling runtime symbols,
and the mangled names are MSVC-mangled. vcpkg built the dependencies with MSVC — correct for the
`x64-windows-static-md` triplet — and then MinGW's `ld` was asked to link them.

**Root cause:** `CMakePresets.json` sets `"generator": "Ninja"` on the `base` preset. Unlike the
Visual Studio generator, Ninja performs no MSVC toolchain discovery — the compiler must already be
on PATH with the MSVC environment initialised (`vcvarsall`). The workflow never does this
(`grep -ci 'msvc-dev-cmd\|vcvars\|ilammy' .github/workflows/ci.yml` → 0), so CMake selects the
first compiler it finds, which on GitHub's Windows image is MinGW at `C:\mingw64`.

This also silently violated a hard project constraint: PROJECT.md and doc 00 §4 specify
**Visual Studio 2022 (v143)** for Windows. The artifact produced was MinGW-built.

## Defect 2 — no preset sets `CMAKE_BUILD_TYPE`; everything is a debug build

```
$ grep -E '^CMAKE_BUILD_TYPE:' build/x64-linux/CMakeCache.txt
CMAKE_BUILD_TYPE:STRING=          # empty

$ grep -o 'vcpkg_installed/[^;"]*debug/lib' build/x64-linux/CMakeCache.txt
vcpkg_installed/x64-linux/debug/lib
```

No configure preset sets `CMAKE_BUILD_TYPE`, and Ninja is a single-config generator, so every
build — local and CI — is an unoptimised no-build-type build linked against vcpkg's **debug**
dependencies. This is why the Windows log shows `Catch2d.lib` rather than `Catch2.lib`.

Consequences beyond tidiness:
- **BUILD-04** claims the artifact is the release binary. It is not.
- **PERF-01/02/03/04** (Phase 5–7) are release blockers — ≤ 3 s metadata pass, ≥ 4× realtime
  content pass. Measured against a debug build linked to debug FFmpeg they are meaningless, and
  would be measured that way today.

## Tasks

### Task 1 — initialise the MSVC environment on the Windows leg

**Files:** `.github/workflows/ci.yml`

**Action:** Add a step to the `build` job that initialises the MSVC x64 developer environment on
Windows only (`if: runner.os == 'Windows'`), placed **after** Checkout and **before** the
`Configure` step — it must precede vcpkg bootstrap/install too, so vcpkg and our project agree on
one toolchain.

Preferred mechanism is `ilammy/msvc-dev-cmd`, the standard action for Ninja+MSVC in Actions.
**Pin it to a full commit SHA, not a floating tag** — `01-RESEARCH.md` § Security Domain lists
supply-chain compromise (ASVS V10) as an applicable threat for this phase, and an unpinned
third-party action is exactly that surface. Add a trailing comment naming the version the SHA
corresponds to.

If a third-party action is judged unacceptable, the dependency-free alternative is invoking
`vcvars64.bat` via `cmd` and exporting the resulting environment to `$GITHUB_ENV`. Either is
acceptable; record which was chosen and why.

Add a comment recording *why* this step exists — that Ninja does no MSVC discovery, so removing it
silently reverts the Windows build to MinGW and reintroduces a link failure that costs a full
FFmpeg build to rediscover.

**Verify:**
- `.github/workflows/ci.yml` parses as YAML
- The MSVC setup step exists, is gated to `runner.os == 'Windows'`, and appears before both the
  vcpkg bootstrap and the Configure step
- If a third-party action is used, its `uses:` references a 40-character commit SHA

**Done:** The Windows leg initialises MSVC before any compilation, so CMake selects `cl.exe`
rather than MinGW's `g++`.

### Task 2 — build Release

**Files:** `CMakePresets.json`

**Action:** Set `CMAKE_BUILD_TYPE` to `Release` in the `base` configure preset's `cacheVariables`.
All five triplet presets inherit from `base`, so one edit covers every leg and local development.

Do not touch anything else in the presets file — it is owned by plan 01-01 and this task's remit
is the build type alone.

**Verify — this one has real regression risk, so run it, do not reason about it:**
- Reconfigure and rebuild `x64-linux` locally. vcpkg already installed both debug and release
  dependency variants, so this relinks rather than triggering a ~40-minute FFmpeg rebuild —
  confirm that is what happens and report the wall-clock.
- `CMAKE_BUILD_TYPE:STRING=Release` in `build/x64-linux/CMakeCache.txt`
- The build still succeeds **under warnings-as-errors**. `-O3` enables optimisation-dependent
  diagnostics (`-Wmaybe-uninitialized` and friends) that `-Wall -Wextra -Werror` will now
  promote to errors. If new warnings appear, fix them properly — do not weaken the warning flags,
  which are BUILD-05's requirement.
- `ctest --test-dir build/x64-linux` is still 10/10
- The linked dependencies come from the release tree, not `debug/lib`

**Done:** Local and CI builds are Release, linked against release dependencies, and the full test
suite still passes with warnings-as-errors intact.
