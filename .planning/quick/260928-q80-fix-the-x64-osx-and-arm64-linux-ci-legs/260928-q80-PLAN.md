This is a permanent readability fix on all five legs, not a throwaway probe. The real arm64-linux fix is the next round, once CI shows the message.

<design_decisions>
- **QD-1 (preset, not a CI flag).** `CMAKE_OSX_ARCHITECTURES` goes in the x64-osx configure preset's `cacheVariables`, not on the CI command line, so a developer's local `cmake --preset x64-osx` gets the same correct build. The triplet feeds vcpkg's ABI hash and this variable does not, so the NuGet cache keeps hitting. Evidence: `vcpkg/scripts/buildsystems/vcpkg.cmake:276-307` reads `CMAKE_OSX_ARCHITECTURES` only to auto-detect a triplet when `VCPKG_TARGET_TRIPLET` is unset, and here it is set explicitly. It stays consistent anyway, since x86_64 maps to x64. The project's own CMake has no arch-keyed logic, only the `if(APPLE)` framework link at `CMakeLists.txt:316`, and those system frameworks are universal.
- **QD-2 (Rosetta step placement).** The orchestrator required the Rosetta step to run before Build. This plan puts it directly before **Configure**, which also satisfies that, for two reasons:
  - it fails fast, ahead of the vcpkg restore;
  - it also covers any configure-time `try_run` a future change might add. None exists today.

  The probe uses absolute paths, `/usr/bin/arch` and `/usr/sbin/softwareupdate`, so a Homebrew-installed `arch` on PATH can never shadow the system tool.
- **QD-3 (artifact arch assertion, planner's discretion).** This step was not in the orchestrator's list. It exists because a leg named x64-osx that silently builds host-arch arm64 would duplicate arm64-osx and report a false green, which is the "gate that quietly stops gating" defect class the file's comments already guard against. It uses `lipo -archs`, is x64-osx-scoped, and sits between Build and Test.
- **QD-4 (NuGet capture shape).** Both NuGet steps get a byte-identical fetch block, so every leg's failure in this step becomes readable, not just arm64-linux's:
  - Variables are `FETCH_OUT="$RUNNER_TEMP/vcpkg-fetch-nuget.stdout"`, `FETCH_ERR="$RUNNER_TEMP/vcpkg-fetch-nuget.stderr"` and `FETCH_RC`.
  - The exit status is captured errexit-safely with `|| FETCH_RC=$?`, because Actions runs `bash -e -o pipefail`.
  - The ::error:: annotation is a fixed string plus the integer exit code. No captured text is interpolated into it, because workflow-command messages need %-escaping.
- **QD-5 (Windows and macOS safety of QD-4).** The NuGet steps also run on the three BLOCKING legs.
  - Redirecting to `"$RUNNER_TEMP/..."` from Git Bash uses the same Windows-path convention the file already relies on for `>> "$GITHUB_ENV"` and `>> "$GITHUB_OUTPUT"`.
  - A file redirect and the old pipe are both non-tty sinks, so vcpkg emits identical bytes and `tail -n 1` yields the same NUGET_EXE.
  - Only `[ ]`, `tail -n 1`, `cat` and plain redirections are used, all bash-3.2 and BSD-safe.
- **Evidence gathered at planning time (2026-09-28, this Linux x64 host):**
  - A real failing `vcpkg fetch nuget` (vcpkg 2026-07-27-98d7cb0) wrote its whole error text to **stdout** and left stderr **empty**. That confirms the swallowing mechanism.
  - `vcpkg fetch --debug` prints `[DEBUG] To include the environment variables in debug output, pass` a separate flag. Plain `--debug` does NOT dump the environment, where the step's credential lives.
  - The fake-vcpkg harness run against base 9598025's read-write step exited non-zero with a **0-byte** log. That is the CI symptom, reproduced locally.
</design_decisions>
