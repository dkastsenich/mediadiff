## true-peak-cross-platform — audio.loudness.true_peak swung 1.7 dB between CI legs because the fixture's own recipe carried a resampler
- **Date:** 2026-09-22
- **Error patterns:** passes on x64-linux fails on arm64-osx and x64-windows-static-md, expect_declared_set "non-pass finding id(s) occurring MORE often than declared", audio.loudness.true_peak, "delta -1633000/1000000dB exceeds tolerance", 0.3dB tolerance, integration.timeline_av_sync ROADMAP SC1, timeline_drift_base.mp4 vs timeline_drift_linear.mp4, --profile sw-encoder, true peak -15.964 vs -17.697 dBTP, libebur128, EBUR128_MODE_TRUE_PEAK, decode_path_class class1 on both sides, integrated loudness agrees to 0.001 LU but true peak does not, aresample, asetrate, libswresample SIMD, audio.silence.edges undeclared finding
- **Root cause(s):** AND-gate, both conditions required simultaneously. (1) DATA/PROCESS — media fixtures are gitignored and regenerated on EVERY CI runner, so the legs never compared the same bytes. Necessary but not sufficient: 160+ other fixtures are equally regenerated per runner and do not fail. (2) DATA — `timeline_drift_linear.mp4` was the ONLY fixture in the entire 143 KB `scripts/gen_corpus.sh` generated through a resampler (`asetrate=48048,aresample=48000`), and libswresample carries hand-written per-architecture SIMD, so its PCM came out different on x86, on aarch64 and on the C reference path. That perturbation is a few LSBs and does NOT move the source peak at all (proven: capture both filter graphs losslessly, true-peak delta exactly 0). The native AAC encoder downstream amplified it NON-LINEARLY into a multi-dB swing in the DECODED true peak, because the decoded peak sits 2–4.6 dB ABOVE the source peak and is dominated by lossy-codec ringing — which of many near-equal ringing candidates wins the `max` is effectively a coin flip under any input perturbation. Measured −15.964 dBTP (x86 SIMD), −13.500 (C reference), −17.697 (arm64-osx). `audio.loudness.true_peak` was CORRECT throughout; the defect was in the fixture, not the check, the decoder, libebur128 or the tolerance.
- **Fix:** `scripts/gen_corpus.sh` — reach the identical 0.1% clock error with ZERO DSP: `sine=...:sample_rate=48000,asetrate=48048,aresample=48000` → `sine=...:sample_rate=47952,asetrate=48000`. `asetrate` is a pure metadata relabel; 47952 × 20s = 959040 whole samples and 48000/47952 = 1.001 exactly, so the drifted arm needs no fractional-sample rounding. Tolerance UNCHANGED, declared finding set UNCHANGED, check sensitivity UNCHANGED. Measurement-neutral: `timeline.av_drift` reports the IDENTICAL rational rate (−54717060000/907751640 ms/min) in all four {old,new} × {simd,C-ref} configurations, pattern still `linear-drift`, `content.audio.sample_hash` still "block 0, 201 divergent blocks". Also removes a SECOND, undeclared `audio.silence.edges` finding the same pair leaked on a foreign DSP path that CI had not yet surfaced. Commit 476f4c5. The earlier attempted fix `f7ce12d` (class-gating loudness on `decode_path_class`, new `SkipReason::cross_platform_decode_noise`) was REVERTED in ab9e908: its premise — libebur128's float true-peak not being bit-identical across platforms on non-class-1 paths — is disproven, and it provably could not fire (both sides were class1). The `decode_path_class` evidence key itself was KEPT as diagnostic-only (inert at comparison time; `kPreconditionKeys` is read only by `compare_hash()` and these checks are `tol`-semantic), because it is what eliminated decoder nondeterminism in this investigation.
- **Files changed:** scripts/gen_corpus.sh, tests/golden/CORPUS_DIGEST.txt, tests/golden/CORPUS_DIGEST_PROVISIONAL.txt, tests/integration/coverage_pairs.h, tests/integration/test_timeline_av_sync.cpp (476f4c5); src/compare/tol.cpp, src/core/model.h, src/report/junit.cpp, docs/schema/report-1.0.json, tests/unit/test_measurement_provenance.cpp, src/analyzers/audio/loudness.cpp, docs/checks/audio.loudness.true_peak.md, docs/checks/audio.loudness.integrated.md, .planning/WINDOWS.md (ab9e908)
- **Why not caught:** No gate existed for this class. Nothing in the repo constrains what DSP a `gen_corpus.sh` recipe may put in a fixture's own generation path, and nothing flags "this recipe contains an arch-divergent block feeding a lossy encoder". Local `ctest` only ever sees one host's bytes, so the exposure is invisible until a foreign leg runs. It stayed latent for a whole phase: the recipe landed in Phase 5, and only Phase 6's new libebur128 sink gave it a `max`-shaped comparator sensitive enough to see it. Phase 6's own loudness fixtures are lossless FLAC (D-13) and byte-stable, so the new check looked cross-platform clean on everything it was designed against.

(d) `CORPUS_DIGEST_PROVISIONAL.txt` entry + `scripts/lint_corpus_digest_provenance.sh`, keeping the locally-predicted hash from being mistaken for a transcribed one. (e) `docs/checks/audio.loudness.true_peak.md`'s new note: "If this check ever again disagrees across platforms, establish that both sides are the same bytes BEFORE suspecting the measurement." GREEN: same test, same foreign DSP path, new recipe — pass. Control: red/green differ by the recipe alone, same host, same binary, same assertion. Post-revert full pre-flight: gen_corpus + check_corpus + lint_bash4_builtins + lint_corpus_digest_provenance + lint_eng16 all exit 0; build clean under warnings-as-errors; **ctest 1195/1195 pass** with the same 6 pre-existing designated-leg-only skips; `verify.schema-drift 06` → `block: false`. - **Related ledger entries:** WINDOWS **#37** (this deviation — marked fixed, description rewritten to record the disproven premise rather than preserve it). Same class: `corpus-fixture-byte-drift` and `test-898-ci-nonreproducible`, both below/above in this file.
- **Transferable heuristic:** This is the THIRD "green locally, red on CI" in this project to resolve as *the hosts were not comparing the same bytes*, and the first two are what cracked it — read this file first, every time. The new signature to carry forward: **when a fixture is generated, not committed, audit its RECIPE for arch-divergent DSP before auditing the code that measures it.** A resampler, an `atempo`, any hand-SIMD filter in a generation path is a per-host input, and a lossy encoder downstream is an amplifier — a few-LSB input delta that provably cannot move the source peak becomes multi-dB after AAC, because the decoded peak is codec ringing, not signal. Also: beware a discriminator that proves less than it seems. "Integrated loudness agrees to 0.001 LU, therefore both platforms analyse identical samples" was the load-bearing premise of the wrong hypothesis and it was unsound — integrated loudness is a gated MEAN and absorbs an LSB-level perturbation, while true peak is a MAX over exactly the ringing that perturbation reshuffles. Two comparators over the same samples can have opposite sensitivity to the same difference; agreement from one is not evidence of identical input. Finally: a gate that cannot fire on the failure it was written for is not harmless — f7ce12d stood ready to silence genuine loudness regressions on all lossy audio on the strength of a mechanism that does not exist.
